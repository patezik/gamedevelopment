# SRV-013 — Штатная сборка Session Server с WebSocket и QR

## Описание

`createSessionServices` из SRV-002 собирает REST и pairing. Шлюз по умолчанию создаётся
без `sessions`, поэтому не находит токены из этого REST. Сервисы QR и матрицы требуют
явных зависимостей. В действующей ветке `qr.scan` отправляет `qr.result`, но результат
успешного `Session.dispatch` не попадает в общую рассылку шлюза.

## Цель

Штатный процесс создаёт дело через полный шлюз генерации, узнаёт обе роли по выданным
токенам и доставляет результат игрового скана на оба клиента.

## Scope

- Расширить существующий вход сборки. REST, `PairingService`, `SessionGateway` и QR
  используют один `SessionManager`. Передать шлюзу `snapshot` и `events` из SRV-010.
- Передать в движок отдельный `EvidenceTokenStore` и привязать его к тому же объекту
  `Session` до публикации. Зарегистрировать pairing- и evidence-матрицы с авторизацией
  desktop, текущим pairing-кодом и минутой из движка.
- После успешного `qr.scan` направить результат того же `dispatch` (версию, события,
  исход) в штатную рассылку по ролям. Сохранить очередь действий, одноразовость
  токена и маршрутизацию `captureEvidence` через QR.
- Оставить фабрику доступной из нативного `npm start`, с явным путём к контенту
  для упаковщика INT-005.

## Out of Scope

- Реализация проекций и фильтра (SRV-010), новые схемы протокола и изменение
  требований валидатора.
- Полный бот и 10 seed (INT-002), проверка с физическим телефоном (INT-001),
  Node SEA и Godot ServerLauncher (INT-005), сохранения (SRV-014/015).

## Ожидаемый результат

Работает серверный маршрут `create → pair → hello → examine → evidence-qr → qr.scan`
для настоящего дела. Будущая загрузка сохранения сможет подключить восстановленный
движок к той же сборке.

## Критерии приёмки

- [x] Публичный пресет и как минимум один seed дают HTTP 201 через реальный генератор
  с полным шлюзом. Оба клиента видят свои `welcome` и представления одной сессии.
- [x] Игровой QR выпускается при осмотре, матрица доступна desktop, скан телефона
  ровно один раз меняет состояние. Оба клиента получают `view.update` одной
  версии, ожидающий скан исчезает, снимок есть в галерее.
- [x] Повторный и чужой скан не тратят время и не публикуют повторное обновление.
  Запрещённая роль не получает матрицу и не может зафиксировать улику напрямую.
- [x] Нативный процесс запускается. Истина и серверные данные отсутствуют
  в ответах и событиях до концовки.
- [x] `npm run tasks:check` и проверки CI зелёные.

## Требования к тестированию

- Smoke штатного процесса, интеграционный тест через ту же фабрику, REST и два
  реальных ws-клиента. Использовать seed, принятый штатным шлюзом. Проверить две
  сессии, повторный скан и обновления обеих ролей сразу после первого скана.
