# VAL-003 — Планировщик по времени: V-TIME-FEASIBLE и SolutionPath

## Описание

Решение должно укладываться в отведённое время (validation.md §3).

Блокировка: план → GameEngine → claims проверен на интеграционных делах и контрольной
сборке санатория. Для приёмочного замера на полном сгенерированном деле нужны улики и
упаковка расследования (GEN-009…011) и правило вывода средства в MVP-контенте (CNT-004).
Фиксация QR из ENG-004 поддержана: планировщик отправляет `captureEvidence` от роли телефона.
Контрольный бенчмарк использует тестовые улики и дополнительное правило средства.

## Цель

Каждое расследование имеет найденный машиной путь решения с запасом времени.

## Scope

- Beam search (ширина 8) по действиям с реальными стоимостями и расписаниями NPC (через GameEngine в режиме симуляции).
- SolutionPath — список PlayerAction.
- V-TIME-FEASIBLE: путь ≤ 70 % длительности.

## Out of Scope

- Учёт сокрытия улик (VAL-005).

## Зависимости

- [VAL-002](VAL-002.md) — Солвер решаемости: V-REACHABLE, V-CULPRIT-PROVABLE, V-UNIQUE
- [ENG-001](ENG-001.md) — GameEngine: агрегат состояния, dispatch, действия move и wait

## Затрагиваемые модули

- `packages/validator/src/planner`

## Ожидаемый результат

Планировщик.

## Критерии приёмки

- [x] SolutionPath, воспроизведённый через GameEngine, приводит к установлению M/M/O виновника.
- [ ] Время работы ≤ 300 мс на расследование MVP.
- [x] `npm run tasks:check` и проверки CI зелёные.

## Требования к тестированию

- Integration: план → движок → claims.
- Регрессии: несколько виновников (нужна полная тройка M/M/O у каждого, путь не теряется при
  росте бюджета 37…60 мин), завершающее сценарий действие отклоняется, бесплатное действие не
  повторяется в ту же минуту, QR-улика фиксируется телефоном и воспроизводится от роли `phone`.
  Каждый тест подтверждён временной мутацией.
- Контрольный бенчмарк: `node --experimental-transform-types tools/bench-planner.ts`.
  Node 24.11.1, Windows, итоговый код на main от 2026-11-25 (с ENG-004): путь из 7 действий,
  52 игровые минуты. Шесть серий по 10 запусков прошли: успешный поиск 139,7…202,5 мс
  (медиана ≈ 146 мс); вариант с удалённой уликой возвращает `TIME_SEARCH_LIMIT` за
  228,7…276,0 мс (медиана ≈ 238 мс). На промежуточных версиях под фоновой нагрузкой две серии
  из 18 упали на одиночном замере отрицательного варианта (319,7 и 373,8 мс). Чередующийся
  A/B-замер: понижение повторных действий добавляет отрицательному варианту ≈ 8 мс.
