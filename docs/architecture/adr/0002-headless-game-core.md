# 0002. Авторитетное headless Game Core на TypeScript, Godot — клиент представления

- **Статус:** Accepted (требует подтверждения владельца проекта — см. [OQ-01](../../planning/open-questions.md))
- **Дата:** 2026-10-30
- **Связанные задачи:** FND-009, ENG-001, SRV-001, GDT-001

## Контекст

Требования:

- Генератор сценариев, Truth Model, TimeSystem, Character Simulation и Investigation Engine должны
  тестироваться **без запуска Godot и мобильного приложения**.
- Нужна массовая проверка расследований на тысячах seed в CI.
- Телефон должен проверять игровые QR-токены **на сервере**; сервер должен знать, какие улики
  существуют, где и когда их можно собрать.
- Состояние телефона (сообщения, контакты, галерея) и состояние основной игры должны быть
  согласованы; два источника истины недопустимы.
- Godot обязателен для desktop-клиента; основной язык — GDScript.

## Рассмотренные варианты

1. **Логика в GDScript внутри Godot, сервер — ретранслятор.**
   + Вся игра в одном движке. − Сервер не может проверить QR без копии игровой логики либо доверия
   клиенту; массовые прогоны требуют Godot headless в CI (медленнее, слабее инструменты
   property-тестирования); телефон получает данные «из вторых рук» через Godot; риск рассинхронизации.
2. **Логика в GDScript, продублированная частично на сервере.** − Двойная реализация, гарантированная
   рассинхронизация. Отклонено.
3. **Headless Game Core на TypeScript, исполняется сервером сессии; Godot и телефон — клиенты.**
   + Один источник истины; общий язык и схемы с мобильным приложением; быстрые детерминированные
   прогоны в Node.js; сервер сам проверяет QR. − Desktop-игра требует локального процесса сервера;
   Godot-клиент ограничен представлением и вводом; задержка на каждое действие (локально — единицы мс).

## Решение

Вариант 3.

- `@hs/core` — чистая, детерминированная, не зависящая от UI библиотека правил.
- `apps/server` хостит экземпляр `GameEngine` на каждую сессию и является **авторитетом** состояния.
- **Godot отвечает за игровой опыт**: сцены, отрисовку, UI, ввод, аудио, визуальные хоррор-эффекты,
  анимации, локальные UX-состояния (открытые панели, выбор, подсказки). Godot отправляет намерения
  игрока (`PlayerAction`) и получает `PlayerView`.
- **Mobile** отвечает за виртуальную ОС, камеру и отображение `PhoneView`; отправляет действия телефона.
- Истина (`TruthModel`, знания NPC, виновник) **никогда не покидает сервер**, кроме debug-режима,
  явно включённого флагом `HS_DEBUG_TRUTH=1`.

### Модель развёртывания

- **Разработка:** сервер запускается `npm run dev:server`; Godot подключается к `http://127.0.0.1:7420`.
- **Релиз (план, INT-005):** сервер собирается в самостоятельный исполняемый файл (Node.js Single
  Executable Application) и запускается Godot-клиентом как дочерний процесс на компьютере игрока.
  Телефон подключается к нему по локальной сети (LAN). Облачный ретранслятор рассматривается
  отдельно (INT-008).

## Последствия

- Ядро тестируется Vitest без Godot; seed sweep выполняется в CI за минуты.
- Godot-клиент не содержит игровых правил; любые правила в GDScript — дефект архитектуры
  (исключение: чисто визуальные эффекты, зависящие от уже полученных значений, например искажение
  экрана по уровню рассудка).
- Требуется стабильный протокол (ADR 0009) и упаковка сервера для релиза (риск R-03).
- Если владелец проекта отклонит решение, альтернатива — вариант 1; задачи фаз 2–4 тогда переносятся
  в GDScript, а сервер упрощается до ретранслятора с регистрацией QR-токенов. Это изменение
  затрагивает около 60% бэклога, поэтому вопрос вынесен в OQ-01 как блокирующий для фазы 2.
