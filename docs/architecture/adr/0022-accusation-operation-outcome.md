# 0022. Исход необратимого обвинения после переподключения

- **Статус:** Accepted
- **Дата:** 2026-11-26
- **Связанные задачи:** PROTO-005
- **Заменяет / заменён:** —

## Контекст

Шлюз отправляет `action.result` только в текущий сокет и не кладёт его в буфер возобновления
([protocol.md §7](../../backend/protocol.md)). Если связь оборвалась после исполнения `accuse` с
`confirm: true` и до доставки результата, клиент не может узнать исход: прощённое ложное обвинение
не оставляет в `PlayerView` следа, а `stateVersion` растёт от любого действия. До этого решения
Godot блокировал новое обвинение в игре навсегда (GDT-009), даже если запрос не дошёл до сервера.

## Рассмотренные варианты

1. Класть `action.result` в буфер возобновления. Закрывает только `resume` в пределах удержанной
   истории; при `resync` исход теряется.
2. Признак «обвинение совершено» или счётчик обвинений в `PlayerView`. Рост счётчика может
   относиться к другой операции, а равенство не исключает позднего исполнения.
3. Устойчивый ID операции от клиента и серверный исход, привязанный к паре «сессия и ID».
   Повтор того же запроса даёт исход, не исполняя действие второй раз.

## Решение

Вариант 3.

- `accuse` получает необязательное поле `operationId` (непустая строка). Для `confirm: true`
  шлюз его требует: без него — `action.result { ok: false, error: ACTION_INVALID }`, движок не
  вызывается. Для `confirm: false` поле не нужно. Клиент создаёт ID один раз на подтверждённое
  обвинение и сохраняет его при переподключении и повторе того же `caseFile`.
- Шлюз хранит операции в памяти объекта сессии (`Session`) и регистрирует операцию синхронно,
  до `await session.dispatch`. Повтор с тем же ID и тем же `caseFile` (сравнение без учёта порядка
  ключей) получает результат первой операции: сохранённый или ожидает ещё идущий.
  Движок вызывается не более одного раза на ID. Результат повтора — обычный `action.result` с
  новым `requestId` и теми же `ok`, `error`, `minutesSpent`, а также `operationId` и (для
  `ok: true`) `stateVersion`, который произвело исполнение. Рассылка `view.update` и событий
  делается только при первом исполнении.
- Повтор с тем же ID и другим `caseFile` получает `ACTION_INVALID`, ничего не исполняется.
- Область хранения: на срок жизни объекта сессии, без вытеснения. Максимум 64 операции на сессию;
  сверх лимита — `RATE_LIMITED`. Игровые правила ограничивают число обвинений, поэтому лимит не
  достигается обычной игрой, а отсутствие вытеснения гарантирует, что известный ID не исполнится
  заново. Исходы не сохраняются на диск: после перезапуска сервера или повторной загрузки игры ID
  считается новым. Это допустимо: итог исполненного обвинения уже входит в сохранённое состояние
  игры (`ending` в снимке), а не исполненное повторяется впервые.
- Роль проверяется прежним `ACTIONS_BY_ROLE`: `accuse` доступен только desktop. Запись
  принадлежит сессии, а не соединению или токену: другая сессия с тем же ID её не видит.
- Замена desktop-пира: запрос закрытого сокета, не начавший исполняться, не выполняется
  (очередь сокета останавливается при закрытии). Уже идущее исполнение завершается и сохраняется;
  вход нового сокета ждёт очереди сессии, затем клиент повторяет запрос и получает сохранённый
  исход. `resync` после выпадения истории не влияет: хранилище операций не связано с буфером.
- Исход не раскрывает истину: поля `operationId` и `stateVersion` — идентификатор клиента и
  номер версии; `culpritIds`, `veracity`, `truth` по-прежнему только на сервере. Сама концовка
  приходит как раньше — `ending` в `PlayerView`.
- Клиент (Godot, `AccusationLedger`): при `UNKNOWN` после подключения к той же игре отправляет
  тот же `caseFile` с тем же `operationId`. Ответ `ok: true`, у которого `stateVersion` не больше
  версии текущего снимка без `ending`, значит «обвинение прощено, игра идёт»; иначе ожидается
  снимок. Отказ `ok: false` возвращает к выбору.

Общий механизм идемпотентности для остальных действий не вводится.

## Последствия

- Игрок не теряет возможность обвинить из-за потерянного ответа, а повтор не удваивает
  обвинение. Реальное повторное обвинение после перезапуска сервера возможно, но состояние игры
  уже сохранено вместе с результатом первого.
- Старые клиенты без `operationId` не смогут подтвердить обвинение: нужен релиз клиентов вместе
  с сервером (все компоненты в одном репозитории).
- Обновлены: `@hs/protocol` (схемы, фикстуры), шлюз, Godot ledger,
  [protocol.md](../../backend/protocol.md) §3, §4, §7, [godot-client.md](../../desktop/godot-client.md) §4.4.
