# 0016. Физические ключи для запертых переходов

- **Статус:** Accepted
- **Дата:** 2026-11-21
- **Связанные задачи:** SIM-001, TRUTH-003, WORLD-002
- **Заменяет / заменён:** —

## Контекст

OQ-18 возник из-за того, что SIM-001 открывала дверь по допуску из `Character.access`,
а TRUTH-003 проверяла фактическое владение предметом. Ключ может лежать в локации,
передаваться между персонажами и перемещаться вместе с контейнером.

## Рассмотренные варианты

1. Допуск персонажа как самостоятельное право открыть дверь. История передачи ключа
   при этом не определяет, кто может им воспользоваться.
2. Физический предмет с явным начальным размещением и историей владения.

## Решение

В MVP запертое ребро открывается физическим ключом, который находится у персонажа в минуту
отправления. Источник владения — `ItemRegistry`, включая владельца внешнего контейнера.
`Character.access` не создаёт начального владения. Запись `move` ссылается на конкретный
использованный ключ и на единственную локацию назначения.

## Последствия

- Передача действует с минуты записи в реестре. Изменения в эту минуту обрабатываются до
  симуляции отправления. Получение в пути или в точке прибытия не разрешает уже начатый переход.
- Будущие перемещения ключа, известные раннеру, ограничивают длительность ожидания. Для
  ещё не записанных запланированных передач раннер может получить `itemChangeMinutes`.
  Новая информация учитывается на ближайшем решении. Уже записанный `stay` неизменяем.
- Проверка явного `move` может найти использованный ключ по цели `item` и сверить реестр.
