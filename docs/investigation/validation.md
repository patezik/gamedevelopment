# Валидация процедурных расследований

Валидатор (`@hs/validator`) — обязательный шлюз генерации ([ADR 0006](../architecture/adr/0006-generation-pipeline.md))
и инструмент массовой проверки пресетов.

## 1. Проверки

| ID | Проверка | Severity | Как |
|----|----------|----------|-----|
| `V-TRUTH-INV` | Инварианты Truth Model | error | `checkTruthInvariants` (инварианты 1–5 и 7; проверка инварианта 6 — [OQ-13](../planning/open-questions.md)) |
| `V-TIMELINE` | Корректность хронологии: события внутри сценария, расписания без дыр, переходы между блоками расписания возможны (скорость перемещений по журналу — инвариант 2 в `V-TRUTH-INV`) | error | проход по журналу и расписаниям, подробности в §7 |
| `V-CULPRIT-PROVABLE` | Виновник доказуем: достижимые улики устанавливают мотив, средство и возможность | error | солвер (§2) |
| `V-UNIQUE` | Единственность: каждый другой персонаж исключается хотя бы одним достижимым оправдывающим утверждением (алиби, нет средства, нет доступа) | error | солвер |
| `V-LIES-BREAKABLE` | Каждая ложь, мешающая решению (ложное алиби виновника, ложь, бросающая подозрение), опровергается достижимым фактом | error | анализ показаний |
| `V-TESTIMONY` | Правдивые показания согласуются с истиной; ошибки памяти в пределах `fuzzMinutes` | error | сравнение с истиной |
| `V-REACHABLE` | Все обязательные улики достижимы: локации доступны, предусловия выполнимы, нет циклических предусловий | error | граф обнаружения |
| `V-TIME-FEASIBLE` | Существует план действий, решающий дело за ≤ 70 % длительности сценария | error | планировщик (§3) |
| `V-REDUNDANCY` | Каждый элемент дела (мотив/средство/возможность) поддержан ≥ 2 независимыми путями | warning (error для MVP-пресета) | минимальный разрез |
| `V-CLEANUP` | После пассивной симуляции сокрытия (игрок бездействует) дело остаётся решаемым до момента `t_safe` ≥ 25 % длительности | error | прогон симуляции без игрока |
| `V-PHONE-REQUIRED` | ≥ 30 % обязательных улик имеют `captureMode: qr` | error | подсчёт |
| `V-HALLUCINATION` | Галлюцинации не ссылаются на факты, относящиеся к решению | error | анализ контента |
| `V-DETERMINISM` | Две генерации с одним seed дают одинаковый `investigationHash` | error | повтор генерации |

Проверки показаний (`packages/validator/src/checks/testimony.ts`) читают `ValidationContext.testimony`
— все показания банка вопросов с `veracity` (`collectTestimony` опрашивает каждого свидетеля каждым
вопросом). `V-TESTIMONY` сверяет `true`/`mistaken`-показания `at` и `did` с истиной в пределах
`DEFAULT_TOLERANCE_MINUTES` (30): интервал `at` должен лежать в интервале пребывания, расширенном на
допуск (касание границы допустимо); `did` подтверждается фактом `did` или событием того же актёра,
глагола и места в пределах допуска (наблюдатели помнят `stay` и `move` как `did`, а журнал хранит их
как присутствие). Ложь не сверяется. `V-LIES-BREAKABLE` считает вредной ложь
виновника о себе и любую ложь, называющую другого; `at`-ложь опровергается достижимой уликой
(`detectContradictions`), `did`-ложь — достижимой уликой, чьё событие-источник показывает актёра
в другом месте в названную минуту. Ложь других видов (`motive`, `relation`, ...) пока считается
неопровержимой (нет способа доказать обратное).

### Проверки устойчивости (`packages/validator/src/checks/robustness.ts`, VAL-005)

Входы — `clues`, `deductionRules` (необязательно `statements`); без них проверки падают с
`SOLVER_INPUT_MISSING`. В шлюз генерации (`GENERATION_CHECKS`) они пока не включены
([OQ-33](../planning/open-questions.md)); экспортируются как `ROBUSTNESS_CHECKS`.

- **`V-REDUNDANCY`.** Минимальный разрез размера 1. Для каждого виновника и каждого элемента
  (`motive`, `means`, `opportunity`), которые достижимые улики устанавливают, проверка убирает по
  одному элементу доказательств (улику или показание; зависимые улики `requires: clue` исчезают
  вместе с ней) и повторяет вывод. Если элемент пропал, он держится на одном пути: `SINGLE_PATH`
  (`data.element`, `data.cutSize`, `data.first`). Перебираются только улики и показания, на которых
  стоят утверждения о виновнике (с цепочкой ранее выведенных утверждений и предпосылок), поэтому
  проверка занимает десятки миллисекунд на деле MVP. Не установленные элементы пропускаются: это
  `V-CULPRIT-PROVABLE`. `redundancyCheck` даёт `warning`, `strictRedundancyCheck` (или
  `createRedundancyCheck('error')`) — `error` для MVP-пресета. Замер: на `sanatorium_winter`
  (seed 1, 2, 3, 6, 9) мотив каждого дела держится на одном пути, средство и возможность — на двух.
- **`V-CLEANUP`.** Пассивная игра: игрок бездействует, улики исчезают по собственным срокам
  (`availableUntil` берётся из распада и событий `destroy` журнала истины, то есть из сокрытия и
  порчи). `t_safe = floor(25 % · durationMinutes)`. Проверка пересчитывает решаемость на минуте 0 и на
  каждой минуте исчезновения улики до `t_safe` включительно, уже с оставшимися уликами, и сообщает
  первую минуту, где утерян элемент, который доказывался со всеми уликами: `CLEANUP_CASE_LOST`
  (`minute`, `data.tSafe`, `data.missing`). Улика, пропадающая ровно в `t_safe`, уже потеряна. Ограничения:
  воспроизводится только сокрытие, записанное в журнале; живая реакция NPC (`ConcealEvidence` в
  работающем движке) не моделируется, потому что движок её не подключает; показания не истекают;
  игрок считается начинающим с нуля на каждой минуте.

## 2. Солвер решаемости

Модель «идеального, но не всеведущего игрока»: знает правила обнаружения, но не истину.

1. Построить граф обнаружения: узлы — улики/показания; рёбра — предусловия (нужен ключ,
   нужен пароль из другой улики, нужен контакт, нужна локация в часы доступа).
2. BFS от начального состояния → множество достижимых сведений (без учёта времени).
3. Применить `DeductionRules` → установленные утверждения.
4. Проверить `V-CULPRIT-PROVABLE` и `V-UNIQUE`.

### Реализация (`packages/validator/src/solver`, VAL-002)

- **Входы** (`ValidationContext`): `clues`, `deductionRules` (результат `compileDeductionRules`),
  необязательные `requiredClueIds` (иначе обязательны все улики), `statements` (показания,
  которые игрок может получить в разговоре) и `startLocationId` (по умолчанию первая локация).
  Без `clues`/`deductionRules` проверки падают с `SOLVER_INPUT_MISSING`, а не проходят.
- **`V-REACHABLE`.** Поиск до неподвижной точки: улика достижима, если её локация связана
  с начальной по переходам и выполнены предусловия: `clue` и `password` — улика-носитель уже
  найдена (пароль без носителя недостижим); `item` — предмет есть в сценарии, `contact` — такой
  персонаж есть. Недостижимая улика — `CLUE_UNREACHABLE` с причиной: `location`, `requirement`
  (в том числе зависимость от недостижимой улики) или `cycle` (улика ждёт саму себя).
  **Ограничения:** где лежит предмет и можно ли его получить, не проверяется (достаточно, что он
  существует); существование контакта не означает, что к нему можно подойти; время, часы доступа
  и ключи на дверях не учитываются (VAL-003).
- **`V-CULPRIT-PROVABLE`.** Достижимые улики и показания → `PlayerKnowledge` → `evaluateClaims`
  с окном инцидента из истины (валидатор серверный и истину читать вправе). Для каждого виновника
  должны быть установлены `motive`, `means`, `opportunity`; иначе `CULPRIT_NOT_PROVABLE`
  (`data.missing`). **Ограничения:** игрок узнаёт окно и место инцидента с неопределённостью
  ([investigation-model.md §3](investigation-model.md)), а солвер берёт точные значения из истины
  (локация первого ключевого события); `statements` берутся из контекста как достижимые без
  проверки, что игрок получит их в разговоре.
- **`V-UNIQUE`.** Каждого персонажа, кроме виновных и жертв, исключает достижимое оправдывающее
  утверждение, установленное правилами: `alibi(c, I)` или `no_access(c, I)`, интервал которых
  покрывает всё окно инцидента, либо `no_means(c)` (OQ-19, GEN-014). Иначе `NOT_UNIQUE`
  (`data.accused` = 1, если достижимые улики к тому же обвиняют этого персонажа). Отсутствие
  звена обвинения оправданием не считается. `alibi` требует показания другого персонажа
  (`testimony`), `no_access` — только запись или улику, которая помещает `c` в другое место на
  весь интервал; правило `opportunity` не срабатывает, если окно покрыто `alibi` или `no_access`.
  Правила вывода `no_means` в поставляемом контенте нет: ни один след пока не даёт для него
  посылок (CNT-004), виды утверждений и учёт в `V-UNIQUE` готовы и покрыты тестами.
- Проверки экспортируются как `SOLVER_CHECKS`; в шлюз их подключает генератор
  (`GENERATION_CHECKS` в `@hs/generator`, GEN-011), у которого есть улики и правила.
  `DEFAULT_CHECKS` остался каркасом без них.

## 3. Планировщик по времени

`solve(investigation, options)` возвращает `SolutionPath` (последовательность `PlayerAction`) или
`null`. Для воспроизведения запустите новый `GameEngine` с теми же начальными условиями и передайте
действия по порядку в `dispatch(solutionSource(action), action)`. Шаг `captureEvidence` сервер
отправляет от роли `phone` после проверки QR, остальные шаги — от `desktop`. Это вход для
будущего E2E-бота INT-002.

- **Входы.** Обязательны `timeBudget` в целых игровых минутах, `clues` и `deductionRules`.
  `startLocationId` по умолчанию указывает на первую локацию мира. В `knownIncident` передают
  только место и интервал, уже сообщённые игроку. Без них правила с `$incident.*` не получают
  значений из истины. `createSimulationPorts()` при каждом вызове создаёт независимые порты
  с одинаковым стартовым состоянием, включая настройки стоимости, инвентарь и память свидетелей.
- **Поиск.** Луч сохраняет до восьми продолжений на слой. Действия берутся из `PlayerView`,
  включая темы разговора, предметы для предъявления и фиксацию ожидающей QR-улики по токену из
  `pendingCapture`. Критерии ранжирования учитывают число
  доказанных звеньев у одного персонажа, собранные улики, разнообразие ветвей, тип действия и
  оценку затрат. Повтор действия, уже выполненного на этой ветви, кроме перехода, ранжируется
  наравне с возвратом в посещённую локацию. Повтор того же действия в ту же минуту при тех же
  знаниях не рассматривается. Идентификаторы разрешают равенство. Реальный `dispatch` проверяет доступ,
  списывает минуты и обновляет видимых собеседников по их фактическому присутствию в журнале.
  Первое продолжение получает движок родителя. Для остальных префикс воспроизводится с нулевой
  минуты на отдельном движке с новыми портами, включая их реакции на уже совершённые действия.
  Если повтор отклоняет шаг, завершает игру или даёт другое представление при пользовательских
  портах, проверка возвращает `TIME_REPLAY_MISMATCH`. Токены должны повторяться при одинаковом
  префиксе и независимом запуске портов.
- **Доказательство.** После открытия улики или получения показания `evaluateClaims` читает
  `PlayerKnowledge` этой ветви. Сервер сверяет результат с виновниками только для проверки цели:
  у каждого должны быть установлены мотив, средство и возможность. Действие, после которого
  время сценария истекает (`outcome: 'time_expired'`), не продолжает путь. Список `statements` из
  контекста VAL-002 не даёт показаний планировщику. Возврат первого доказанного пути допускает
  более короткое решение.
- **Проверка.** `timeFeasibleCheck` использует бюджет `floor(durationMinutes × 7 / 10)`, включая
  последнюю допустимую минуту. Проверка экспортируется отдельно. Её подключение к шлюзу GEN-011 требует приёмки бюджета и подготовки контекста симуляции. Ошибки: `PLANNER_INPUT_MISSING` при отсутствии улик или правил,
  `TIME_PATH_NOT_FOUND`, если луч исчерпан без подходящего пути, и `TIME_SEARCH_LIMIT`, если для
  продолжения требуются более 2500 вызовов `dispatch` с учётом воспроизведения префиксов.
  `TIME_INCIDENT_CONTEXT_MISSING` означает, что все правила хотя бы одного обязательного звена
  требуют `$incident.*` в предпосылках, а известной игроку вводной нет. В этом случае поиск не
  запускается. Ограниченный поиск может пропустить существующий путь.

**Ограничения MVP.** ENG-003 проверяет присутствие по интервалам `at` в движке. Для проверки
реального расписания сгенерированное расследование должно содержать соответствующие интервалы.
Ожидающий QR-токен не добавляет улику в знания: её даёт только `captureEvidence`. Для этого
`createSimulationPorts()` должен дать телефон (`phone`) и детерминированный `evidenceTokens`.
Команда `node --experimental-transform-types tools/bench-planner-generated.ts` прогоняет
`sanatorium_winter` для seed `1`, `2`, `3`, `6` через штатный шлюз и использует улики, правила,
память и политики лжи принятой попытки. Для каждого запуска создаются отдельные порты.
Массив готовых показаний используется только для отчёта о входе. Движок получает показания
через порт памяти свидетеля. Симуляция использует присутствие из журнала принятой попытки.
Порты включают `npcSimulation` (ENG-014): без симуляции после минуты 0 в локациях никого нет, и
показания недоступны. Вводная для `$incident.*` задаётся допущением OQ-25: место первого
ключевого события и окно инцидента (как в SRV-012, где они раскрываются после любой обязательной
улики). Это сведения, видимые игроку, а не виновник; планировщик применяет их с первой минуты,
что допустимо, потому что правило сработает только при найденных уликах присутствия.
Результат на `sanatorium_winter` (Node 24, Linux), путь воспроизведён через свежий `GameEngine`,
QR фиксируются ролью `phone`, M/M/O установлены у виновника, конец в пределах 70 % (3024 мин):

| seed | действий | игровых минут | время поиска, мс |
|------|----------|---------------|------------------|
| 1 | 85 | 891 | 1230 |
| 2 | 74 | 664 | 680 |
| 3 | 27 | 208 | 360 |
| 6 | 126 | 1335 | 1270 |

Бюджет планировщика на полном деле MVP — **≤ 2000 мс** (решение владельца 26.11.2026; исходные
300 мс на полном деле не достигаются). Причина: поиск шириной 8 воспроизводит префикс пути для
каждого брата (около 1 мс на `dispatch` в мире на 500 фактов), а путь содержит 27–126 действий.
Раньше путь не находился совсем: лимит в 256 вызовов исчерпывался на ранних уровнях, а бесплатные
`interrogate` по каждой улике ранжировались выше разговоров, поэтому показание о мотиве достижимо
лишь после сотни действий. Теперь разговоры о людях выше `interrogate`, лимит 2500.
`engine.knowledgeSnapshot()` убирает из оценки ветви сериализацию всего мира. Вернуться к 300 мс
можно через дешёвое клонирование движка (снимок с сериализацией мира стоит 6-8 мс и не окупается).
Бенчмарк завершается с ошибкой при отказе поиска или при превышении 2000 мс на любом seed; контрольная
сборка (`tools/bench-planner.ts`) по-прежнему держит 300 мс.

`node --experimental-transform-types tools/bench-planner.ts` проверяет контрольную сборку
с тремя тестовыми уликами и дополнительным правилом средства. Этот замер относится к
контрольному делу.

## 4. Ремонт и перегенерация

При ошибке генератор пытается (детерминированно, по подсиду попытки):
1. добавить избыточный след к недоказанному элементу (если правила следов допускают);
2. сдвинуть расписание невиновного персонажа, чтобы дать ему проверяемое алиби;
3. перегенерировать со стадии IncidentSelection с другим кандидатом;
4. перегенерировать с SocialGen.
Максимум 8 попыток. Отчёт содержит причины каждой неудачи.

Реализовано (GEN-011): стратегии 3–4 как перегенерация с подсидом следующей попытки с первой стадии;
стратегии 1–2 (правка готового дела) — нет. См. [generation-pipeline.md](../procedural-generation/generation-pipeline.md).

## 5. Seed sweep

```bash
npm run sweep -- --scenario sanatorium_winter --count 1000 --from 0
```

Параметры `hs-sweep` (`packages/validator/bin/hs-sweep.ts`): `--scenario` (обязателен), `--count` (1000), `--from` (0),
`--out` (`reports`), `--workers` (по умолчанию `min(4, ядра)`), `--content-dir`, а также пороги
`--max-failure-rate` (0,01) и `--min-entropy-ratio` (0,8). Seed — десятичные строки `from … from+count-1`.
Генерация идёт в `worker_threads` пакетами по 8 seed; отчёт строится после сортировки записей по seed,
поэтому не зависит от `--workers` (кроме раздела `timing`, он зависит от машины). Генератор
подключается динамическим импортом: `@hs/generator` зависит от `@hs/validator`. Код возврата: 0, пороги
выполнены; 1, нарушены (причины в stderr и в `verdict` отчёта); 2, неверные аргументы или сценарий.

Выход: `reports/sweep-<scenario>-<from>-<count>.json` + `.md` (каталог в `.gitignore`):

- доля успешных генераций, распределение числа попыток;
- распределение виновников по архетипам и персонажам, энтропия;
- распределение мотивов и типов инцидентов;
- среднее/максимальное время генерации;
- список проваленных seed с первой ошибкой; причины отклонения всех попыток проваленных seed
  (`IncidentSelection:INCIDENT_NO_FEASIBLE_CULPRIT`, `V-UNIQUE:NOT_UNIQUE` и т. д.);
- доля seed, принятых с первой попытки.

Энтропия виновников считается по персонажам (Шеннон, биты) от `log₂(размер состава)`. Отчёт называет
виновников: это диагностика сервера, его нельзя отдавать клиентам. Отчёт не подгоняется под пороги:
нарушение порога выводится как есть. Замер на момент VAL-007 (GEN-014 не закрыта): `sanatorium_winter`,
1000 seed, 4 воркера, 94 с; генерация удалась для 70,2 % seed (неудач 29,8 %, порог < 1 % нарушен),
энтропия виновников 2,80 из 2,81 бит.

**Пороги для CI:** PR — 1000 seed, неудач < 1 %, энтропия виновников ≥ 0,8 · log₂(N); ночной
прогон — 20 000 seed. Проваленные seed добавляются в регрессионный корпус
`packages/validator/regression-seeds.json` и проверяются в каждом PR.

## 6. Мутационные тесты валидатора

Валидатор тестируется на заведомо сломанных расследованиях: удалить ключевую улику, сделать алиби
виновника неопровержимым, поместить персонажа в две локации, добавить цикл предусловий. Каждая
мутация должна ловиться соответствующей проверкой.

## 7. Каркас валидатора (`packages/validator`)

Проверки независимы и подключаются в общий реестр; запуск — `validateInvestigation(investigation,
{ checks, context? })`. Готовый набор — `DEFAULT_CHECKS` (`V-TRUTH-INV`, `V-TIMELINE`, `V-PHONE-REQUIRED`, `V-DETERMINISM`); новые проверки
(VAL-002 и далее) добавляются в этот массив и не меняют работу существующих.

**Проверка** (`Check`): `id` вида `V-<СЛОВА>` (уникальный в запуске, иначе `RangeError`), `description`
и функция `run(investigation, context)`, которая возвращает находки. Она должна быть детерминированной
и не менять расследование. Если `run` бросает исключение, отчёт получает находку `CHECK_CRASHED`
(`error`): проверка, которая не смогла запуститься, ничего не доказала и не может считаться
пройденной. Остальные проверки при этом выполняются.

**Находка** (`Finding`): `checkId`, `severity` (`error` | `warning`), стабильный `code` (по нему
сопоставляют тесты и ремонт, но не по `message`), `message`, `eventIds` (ссылки на события журнала
истины, первое: где нарушение проявилось), необязательные `subject` (`EntityRef`) и `minute`, а также
`data` (например, номер инварианта).

**Отчёт** (`ValidationReport`): `ok` (нет ни одной `error`: расследование можно отдавать игроку),
`errorCount`, `warningCount`, `checks` (по записи на проверку в порядке запуска: `id`, `passed`,
`findings`) и плоский список `findings` в том же порядке. `warning` не делает проверку и отчёт
проваленными. Отчёт можно записать как canonical JSON.

**Контекст** (`ValidationContext`): сведения о сценарии, которых нет в `Investigation`.
Сейчас это `historyStartMinutes` (пресет `time.historyStartMinutes`, не больше 0): расследование
хранит конец сценария, но не начало предыстории. Если контекст не задан, проверки, которым нужна
эта граница, её пропускают. Остальные поля нужны `V-PHONE-REQUIRED` и `V-DETERMINISM` (см. ниже):
`clues`, `requiredClueIds`, `minQrShare`, `regenerate`; солверу (VAL-002) — ещё `deductionRules`,
`statements`, `startLocationId`. Без них эти проверки **не** пропускаются, а
дают `error` (`PHONE_INPUT_MISSING`, `DETERMINISM_INPUT_MISSING`): непроверенное нельзя считать пройденным.

### `V-TRUTH-INV`

Обёртка над `checkTruthInvariants(truth, world)` ([truth-model.md §4](truth-model.md)): каждое
нарушение инвариантов 1–5 и 7 становится находкой `error`; `code` и `eventIds` берутся из нарушения,
в `data.invariant` — номер инварианта. Инвариант 6 не проверяется (нужны наблюдения персонажей,
вопрос [OQ-13](../planning/open-questions.md)).

### `V-TIMELINE`

Не повторяет `V-TRUTH-INV`: скорость перемещений по журналу — инвариант 2 и сообщается только там.
Проверяет:

| Код | Что нарушено |
|-----|--------------|
| `TIMELINE_EVENT_AFTER_END` | событие заканчивается после конца сценария (`t + duration > durationMinutes`; ровно в конце допустимо) |
| `TIMELINE_EVENT_BEFORE_HISTORY` | событие начинается раньше начала предыстории (`t < historyStartMinutes`; только если контекст задан) |
| `TIMELINE_INCIDENT_WINDOW_AFTER_END` / `…_BEFORE_HISTORY` | окно инцидента выходит за те же границы (ссылки на ключевые события) |
| `CHAR_SCHEDULE_GAP`, `CHAR_SCHEDULE_OVERLAP`, `CHAR_INVALID_SCHEDULE` | расписание персонажа не покрывает сутки целиком без дыр и перекрытий (по `validateRoutine`; `data.minuteOfDay`) |
| `TIMELINE_ROUTINE_UNREACHABLE` | соседние блоки расписания в разных локациях (включая переход последнего блока в первый через полночь), но маршрута между ними нет. Считается, что у персонажа есть все ключи: не проходит только отсутствующая связь или постоянный замок |
| `TIMELINE_ROUTINE_UNKNOWN_LOCATION` | расписание ссылается на несуществующую локацию |

У персонажа с неисправным расписанием переходы не проверяются (порядок блоков ненадёжен).
Проверки по фактам (`at`, `possessed`) на границы не распространяются: факты о прошлом (`since`,
давние владения) могут законно выходить за предысторию.

### `V-PHONE-REQUIRED`

Берёт из контекста все улики дела (`clues`), id обязательных улик (`requiredClueIds`: минимальное
покрывающее множество солвера, повторы считаются один раз) и порог пресета `minQrShare`.
Условие: `qr / обязательных ≥ minQrShare`, где `qr` — число обязательных улик с `captureMode: qr`.
Деление, а не `обязательных × minQrShare` (`10 × 0,3 = 3,0000000000000004`), поэтому ровно 30 %
проходит. Считаются только обязательные улики: необязательные QR-улики не помогают.

| Код | Что нарушено |
|-----|--------------|
| `PHONE_QR_SHARE_TOO_LOW` | доля QR ниже порога (`data`: `qr`, `required`, `minQrShare`; ссылка на событие первой обязательной улики) |
| `PHONE_UNKNOWN_REQUIRED_CLUE` | обязательный id отсутствует среди улик дела |
| `PHONE_NO_REQUIRED_CLUES` | обязательных улик нет, а `minQrShare > 0` (при `0` проходит) |
| `PHONE_INVALID_MIN_SHARE` | `minQrShare` не число из `[0, 1]` |
| `PHONE_INPUT_MISSING` | в контексте нет `clues`, `requiredClueIds` или `minQrShare` |

### `V-DETERMINISM`

Вызывает `context.regenerate()` (повторная генерация с теми же seed, пресетом и версией генератора)
и сравнивает `investigationHash` обоих расследований. `investigationHash` — SHA-256 от canonical JSON
снимка расследования (`stateHash(snapshotInvestigation(...))`), экспортируется как
`investigationHash`.

| Код | Что нарушено |
|-----|--------------|
| `DETERMINISM_HASH_MISMATCH` | хеши различаются (`data.first`, `data.second`) |
| `DETERMINISM_REGENERATION_FAILED` | повторная генерация бросила исключение |
| `DETERMINISM_INPUT_MISSING` | в контексте нет `regenerate` |

### Мутационные фикстуры

`packages/validator/test/mutations.ts` хранит заведомо сломанные варианты тестового расследования
`tinyManor()`: по одной мутации на каждый инвариант (1–5, 7) и на каждый код `V-TIMELINE`, `V-PHONE-REQUIRED`
(кроме `PHONE_INPUT_MISSING`) и `V-DETERMINISM` (кроме `DETERMINISM_INPUT_MISSING`); поля контекста,
которые ломает мутация, задаются в её `context` поверх `cleanContext()`. Коды `*_INPUT_MISSING`
покрыты отдельными тестами. Для
каждой указаны проверка, код находки и нужны ли ссылки на события. Тесты требуют, чтобы мутация
ловилась именно своей проверкой и **не** вызывала находок у остальных, а нетронутое расследование
проходило без находок. Новая проверка добавляет свои мутации в этот список.

### Стоимость проверки показаний

`V-TESTIMONY` повторно использует защитные копии фактов, событий и интервалов присутствия внутри одного запуска проверки. Между запусками копии не сохраняются: изменение расследования заново читается из TruthModel. Проверки и допустимая погрешность памяти остаются прежними.
