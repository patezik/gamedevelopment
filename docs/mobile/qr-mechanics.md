# QR-механики

## 1. Три разных QR — не путать

| QR | Где показывается | Чем сканируется | Формат | Назначение |
|----|------------------|-----------------|--------|------------|
| **QR Expo Go** | терминал / браузер разработчика (`npx expo start`) | приложение Expo Go / системная камера | `exp://…` | **Только разработка**: открыть JS-бандл в Expo Go. Не имеет отношения к игре и не существует в релизе. |
| **QR привязки** | экран привязки Godot | камера **внутри** companion-приложения (экран `/pair`) | `hs1:pair:<host>:<port>:<code>` | Подключить телефон к игровой сессии |
| **QR улики** | оверлей фиксации улики в Godot | приложение Camera виртуальной ОС | `hs1:ev:<sessionTag>:<tokenId>:<sig>` | Зафиксировать улику — игровая механика |

Приложение отклоняет `exp://` и любые неизвестные форматы с понятным сообщением.

## 2. Жизненный цикл QR улики

```
[ядро] игрок изучил точку с clue.captureMode = "qr"
   → EvidenceTokenPort.issue(clueId, expiresAt = now + 120)      (сервер: запись токена)
   → PlayerView.pendingCapture { tokenId, clueTitle, expiresInMinutes }
[Godot] GET evidence-qr/:tokenId → рисует QR в оверлее «Сфотографируйте улику»
[phone] Camera: распознан hs1:ev:… → qr.scan { raw }
[сервер] проверки (по порядку):
   1. формат                      → QR_INVALID
   2. sessionTag == текущая сессия → QR_WRONG_SESSION
   3. HMAC подпись                 → QR_INVALID
   4. токен существует             → QR_INVALID
   5. срок (игровое время)         → QR_EXPIRED
   6. не использован               → QR_ALREADY_USED (идемпотентный ответ с clueRef)
   7. игровые предусловия (игрок всё ещё в локации, жив, не в блокирующем взаимодействии) → QR_PRECONDITION_FAILED
   → engine.dispatch({ type: "captureEvidence", tokenId })  (2 игровые минуты)
   → токен помечен usedAt
[оба клиента] view.update: улика в gallery, pendingCapture снят; event: «Улика сохранена»
```

Токен **не содержит** содержимого улики и не позволяет вывести решение. Срок истёк — игрок
может снова изучить точку (новый токен, снова тратится время).

### Реализация на сервере (`apps/server/src/qr`)

- **Токен.** `EvidenceTokenStore` реализует `EvidenceTokenPort` для одной сессии. `tokenId` — 96
  случайных бит (16 символов base64url). Строка QR: `hs1:ev:<sessionTag>:<tokenId>:<sig>`, где
  `sessionTag` — первые 8 hex-символов SHA-256 от id сессии, `sig` — HMAC-SHA256 от
  `sessionTag:tokenId` под секретом, который не покидает процесс, усечённый до 128 бит (22 символа
  base64url, принимается только каноническая запись: лишние биты последнего символа не дают
  альтернативных строк). В записи токена хранятся `clueId`, `expiresAt` (игровая минута) и `usedAt`;
  содержимого улики в токене и в QR нет.
- **Порядок создания.** Хранилище создаётся до сессии (`QrService.createStore()`), передаётся движку
  как `ports.evidenceTokens`, затем `QrService.attach(session, store)` привязывает его к id сессии.
  В штатной фабрике привязка выполняется в `prepare` до публикации сессии.
- **Проверки `qr.scan`** (`QrService.scan`) идут в порядке выше с двумя уточнениями.
  *«Использован» проверяется раньше «истёк»*: повторный скан уже сохранённой улики всегда отвечает
  `QR_ALREADY_USED` с `clueRef` (идемпотентно), а не `QR_EXPIRED`, даже когда срок давно прошёл.
  *Токен тратится только при успешной фиксации*: отказ движка (`QR_PRECONDITION_FAILED`) или сбой
  (`INTERNAL`) оставляют токен рабочим, игрок может вернуться и отсканировать снова.
- **Рассылка после скана (SRV-013).** `QrService.scan` вызывает `onCaptured` только после первой
  успешной фиксации, с результатом того же `Session.dispatch` и его `stateVersion`. Шлюз передаёт
  обеим ролям новые виды, телефону — `scanResult`. Эти сообщения могут предшествовать `qr.result`.
  Повторный или чужой скан возвращает только отказ; время и версия состояния не изменяются.
- **Одновременные сканы одного QR** фиксируют улику один раз: второй ждёт первого и получает
  `QR_ALREADY_USED`; если первый получил отказ, второй делает собственную попытку.
- **Отказы движка** (`captureEvidence` через `session.dispatch("phone", …)`): `ACTION_NOT_AVAILABLE` и
  `ACTION_BLOCKED` становятся `QR_PRECONDITION_FAILED`; `GAME_OVER`, `SESSION_CLOSED`, `INTERNAL`
  передаются как есть; любой другой код сообщается как `INTERNAL` (внутренности движка не раскрываются).
- **Матрицы.** `renderMatrix` (`qrcode`, уровень коррекции M) возвращает `{ size, modules }`: `modules`
  — `size × size` символов `0`/`1` по строкам, без «тихой зоны» (её рисует Godot). Эндпоинты
  `pairing-qr` и `evidence-qr/:tokenId` описаны в [backend.md §3](../backend/backend.md).
- **Не входит.** Приём сообщения `qr.scan` по WebSocket и рассылка `qr.result` — шлюз (SRV-004),
  который вызывает `QrService.scan(session, raw)`. Саму фиксацию улики выполняет действие
  `captureEvidence` движка (ENG-004). Штатная фабрика `createSessionServices` соединяет
  менеджер, шлюз, сервис привязки и QR с реальным движком (SRV-013).

При сборке дела ядро сохраняет заданные режимы QR и переводит достаточное число
обязательных улик в QR на детерминированном подпотоке. Срок токена ограничен
120 игровыми минутами и моментом исчезновения следа. Движок хранит ожидающую
фиксацию в серверном снимке и повторно использует действующий токен той же улики.

### Оверлей в Godot

Exploration открывает оверлей при появлении `PlayerView.pendingCapture`. Backend запрашивает
`GET /api/v1/sessions/:id/evidence-qr/:tokenId` с desktop-токеном текущей сессии. Оверлей отображает
название улики, чёрно-белую матрицу без сглаживания и белую тихую зону в четыре модуля с каждой
стороны. Остаток срока берётся из `expiresInMinutes` при каждом принятом `view.update`. Телефон
вне сети или без привязки виден по подсказке под QR.

После удаления `pendingCapture` из нового вида оверлей закрывается. «Отмена» и Esc скрывают
его локально. Пока токен есть в представлении сессии, кнопка «Показать QR улики» открывает
оверлей снова и запрашивает матрицу заново. Устаревшие запросы удаляются из очереди, а ответы уже
начатых запросов игнорируются. При сетевой ошибке или неверной матрице доступна кнопка «Повторить».
При HTTP 410 оверлей предлагает снова
осмотреть улику, при HTTP 409 ожидает обновления дела.

### Ручная проверка на физическом телефоне

1. Из корня репозитория запустите команды в PowerShell с Godot 4.7.2. Первая команда импортирует
   проект, вторая открывает оверлей с тестовой матрицей, созданной серверным `renderMatrix`.

   ```powershell
   $env:GODOT_BIN = 'C:\path\to\Godot_v4.7.2-stable_win64_console.exe'
   & $env:GODOT_BIN --headless --path apps/desktop --import
   & $env:GODOT_BIN --path apps/desktop res://tests/manual/evidence_capture_preview.tscn
   ```

2. Наведите камеру физического телефона на экран. Ожидаемая строка —
   `hs1:ev:01234567:AAAAAAAAAAAAAAAA:AAAAAAAAAAAAAAAAAAAAAA`. Системная камера может распознать
   QR как текст, если поддерживает текстовые коды. Если камера показывает только ссылки,
   используйте на том же телефоне QR-сканер с выводом текста. Годится также проверить читаемость
   после изменения размера окна. Зафиксируйте модель телефона, приложение и результат распознавания.
3. Нажмите Esc и затем «Показать QR улики». Матрица должна появиться снова. Этот режим
   проверяет читаемость QR и работу оверлея с тестовым ответом. Строка содержит тестовую подпись,
   поэтому для проверки игровой фиксации потребуется действующий токен реальной сессии.

24.11.2026 пользователь подтвердил, что физический iPhone считывает тестовый QR из окна Godot.
В стандартном приложении Apple «Команды» использовалась последовательность «Сканировать QR-код
или штрихкод» → «Получить текст из QR-кода» → «Показать текст». Получена строка
`hs1:ev:01234567:AAAAAAAAAAAAAAAA:AAAAAAAAAAAAAAAAAAAAAA`. Esc закрыл оверлей, кнопка
«Показать QR улики» открыла его снова. Сквозная проверка с мобильным клиентом остаётся отдельным
сценарием.

После готовности зависимостей сквозной сценарий начинается с запуска сервера
(`npm run start -w @hs/server`), Godot и мобильного клиента по [инструкции для Expo Go](mobile-app.md#8-запуск-в-expo-go).
Компьютер и телефон должны быть в одной сети. Создайте сессию, привяжите телефон, осмотрите
в Exploration точку с `captureMode: "qr"` и наведите камеру виртуального телефона на экран.
Проверьте, что улика появляется в галерее, а оверлей закрывается после `view.update`. Точки для
этого сценария зависят от пресета и seed.

Для сквозного прогона требуются создание и привязка сессии в desktop
([GDT-003](../../tasks/GDT-003.md), [SRV-002](../../tasks/SRV-002.md)), осмотр с выдачей токена
([ENG-003](../../tasks/ENG-003.md)), фиксация на сервере ([ENG-004](../../tasks/ENG-004.md)),
камера с подключением к сессии ([MOB-003](../../tasks/MOB-003.md), [MOB-004](../../tasks/MOB-004.md))
и экран галереи ([MOB-008](../../tasks/MOB-008.md)). Штатный запуск сервера подключает
REST привязки, маршруты QR и шлюз над выданными токенами ([SRV-013](../../tasks/SRV-013.md)). Начальный запуск приложения отслеживается в
[FND-006](../../tasks/FND-006.md).

### QR привязки в Godot (`apps/desktop/src/scenes/pairing`)

Экран Pairing ([godot-client.md §4.7](../desktop/godot-client.md)) получает матрицу текущего кода
через `GET /sessions/:id/pairing-qr` и рисует её тем же `QrTexture`, что и оверлей улики: один
пиксель на модуль, поле тишины 4 модуля, фильтр `NEAREST`, сторона кратна ширине текстуры. Код
и адрес из `qrPayload` выводятся текстом для ручного ввода. Истёкший код заменяется через
`POST /sessions/:id/pairing-code`.

**Ручная проверка на физическом iPhone (монитор 1080p, 50 см).** Штатный сервер ([SRV-013](../../tasks/SRV-013.md)) отдаёт `pairing-qr`;
проверка до сих пор идёт с тестовым адаптером живых тестов (REST той же фабрики
`createSessionServices` плюс `pairing-qr` и шлюз над теми же сессиями), сквозная проверка на
штатном сервере входит в INT-001.

1. Компьютер и телефон в одной Wi-Fi-сети (мобильный интернет телефона не подходит), входящие
   подключения Node.js разрешены ([setup.md §6](../development/setup.md)).
2. Из корня репозитория после `npm ci` выполните скрипт. Он находит LAN-адрес компьютера
   (активный адаптер со шлюзом, без VPN и виртуальных; сначала `192.168.*`, затем `10.*`,
   `172.16–31.*`), проверяет порты 7420 и 8081, зависимости и правило брандмауэра (только чтение,
   настройки сети и брандмауэра он не меняет). Затем открывает окна «GDT-003 server» (адаптер с
   этим адресом в QR), «GDT-003 Expo» (Metro с тем же адресом) и Godot на «Новой игре». `-CheckOnly`
   только проверяет, `-HostAddress <IPv4>` задаёт адрес вручную.

   ```powershell
   powershell -ExecutionPolicy Bypass -File apps\desktop\tests\manual\start_pairing_check.ps1 -GodotBin <путь к Godot_v4.7.2-stable_win64.exe>
   ```

   Без скрипта: адаптер — `node --import tsx apps/desktop/tests/live/pairing_server.mjs --mode=adapter --manual --port=7420`
   (адрес в QR — `$env:HS_PUBLIC_HOST`), мобильный клиент — по [mobile-app.md §8](mobile-app.md#8-запуск-в-expo-go),
   игра — `& $env:GODOT_BIN --path apps/desktop`.
3. В Safari на телефоне откройте `http://<адрес>:7420/api/v1/health`: ответ со `status: "ok"`
   подтверждает, что телефон видит сервер. Отсканируйте камерой QR из окна «GDT-003 Expo» и
   откройте клиент в Expo Go.
   В Godot (окно на мониторе 1080p) выберите сценарий, выключите «Случайный seed», введите
   `winter-42` и нажмите «Создать дело».
4. На экране «Подключение телефона» должны быть QR, код, адрес Wi-Fi, «Игра подключена к серверу»
   и «Телефон не привязан». «Начать расследование» недоступна.
5. Держите iPhone в 50 см от монитора, откройте экран привязки в приложении и наведите камеру
   на QR. Ожидается: приложение принимает QR, в окне адаптера появляется `POST /pair -> 200`,
   приложение переходит на `/os`.
6. Пока у телефона нет WebSocket-клиента ([MOB-003](../../tasks/MOB-003.md)), он не выходит в
   сеть и кнопка остаётся недоступной — это ожидаемо. Активацию кнопки по `peer.status` с
   `phone: "online"` на штатной сборке проверяет [INT-001](../../tasks/INT-001.md).
7. Дополнительно: «Новый код» сменяет код и QR, старый код на телефоне получает
   `PAIRING_CODE_INVALID`; ручной ввод адреса и кода с экрана тоже привязывает телефон.

Запишите монитор (диагональ, разрешение, масштаб Windows), модель iPhone, расстояние, время
распознавания и результат.

### Экран привязки (`apps/mobile/app/pair.tsx`, `src/pairing`)

- `parsePairingQr` принимает только `hs1:pair:<host>:<port>:<code>`: хост из букв, цифр, `.` и `-`,
  порт 1–65535, код из 6 символов алфавита сервера (строго в верхнем регистре). `exp://`, `exps://`
  отвечают подсказкой про QR Expo Go, `hs1:ev:` — подсказкой про QR улики, остальное — «не QR привязки».
  Ручной ввод принимает `host:port` и код в любом регистре.
- `pairDevice` шлёт `POST http://<host>:<port>/api/v1/pair` с фиксированным `deviceName`
  (данные телефона не читаются), таймаут 8 с. Коды ошибок сервера (`PAIRING_CODE_INVALID`,
  `PAIRING_CODE_EXPIRED`, `PAIRING_RATE_LIMITED`, `PROTOCOL_MISMATCH`) показываются понятным текстом;
  сетевой сбой — `NETWORK`, неожиданный ответ — `BAD_RESPONSE`.
- Ответ сохраняется в `expo-secure-store` (ключ `hs.pairing`: адрес, `sessionId`, `deviceToken`,
  `wsPath`), затем экран переходит на `/os`. Подключение по WebSocket — [MOB-003](../../tasks/MOB-003.md).
- Ручная проверка на физическом iPhone со штатным сервером входит в [INT-001](../../tasks/INT-001.md):
  камера, QR, ручной ввод, повторная привязка и восстановление после перезапуска приложения.

## 3. Ошибки камеры (мобильное приложение)

| Ситуация | Поведение |
|----------|-----------|
| Разрешение не выдано | экран объяснения + кнопка запроса; при «больше не спрашивать» — ссылка в настройки ОС |
| Камера недоступна (симулятор, занята) | сообщение и ручной ввод кода (только для QR привязки; для улик — не допускается) |
| Неизвестный формат / `exp://` | «Это не игровой код» |
| Повторное распознавание одного кода | дебаунс 2 с на одинаковое содержимое |
| Нет соединения | код не отправляется; «Нет связи с игрой» |
| Ответ с ошибкой | человекочитаемое сообщение по `ErrorCode` (таблица в `src/os-apps/camera/errors.ts`) |

### Реализация в приложении (`apps/mobile/src/os-apps/camera`)

- `handleScan(raw, deps)` — чистая функция решения: одинаковое содержимое в окне 2 с игнорируется;
  всё, кроме `hs1:ev:`, отклоняется без отправки («Это не игровой код»; для `hs1:pair:` — своя
  подсказка); при отсутствии связи код не отправляется («Нет связи с игрой»). Проверка подписи и
  срока — только на сервере.
- Отправка — `WsClient.sendQrScan` (только после `welcome`, без очереди); `qr.result` кладётся
  в `useQrStore`. Ответ не несёт id запроса, поэтому в полёте считается один скан; при обрыве сокета
  ожидание сбрасывается и игрок сканирует заново.
- `errors.ts` содержит таблицу `ERROR_MESSAGES: Record<ErrorCode, string>`: новый код протокола
  без текста не пройдёт `typecheck`.
- Разрешение камеры: пояснение и кнопка запроса; при `canAskAgain: false` — «Открыть настройки»
  (`Linking.openSettings`). `onMountError` показывает «Камера недоступна»; ручного ввода улик нет.

## 4. Почему улика не вводится вручную

Ручной ввод кода улики не поддерживается: механика задумана как «сфотографировать» улику
телефоном героя. Для доступности (нет камеры) — открытый вопрос OQ-07.
