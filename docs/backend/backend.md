# Session Server (`apps/server`)

Стек — [ADR 0003](../architecture/adr/0003-backend-stack.md). Протокол — [protocol.md](protocol.md).

## 1. Ответственность

- Создание и жизненный цикл игровых сессий; хостинг `GameEngine` на сессию.
- Привязка мобильного устройства (pairing), проверка принадлежности устройства сессии.
- WebSocket-шлюз: аутентификация, роли, heartbeat, порядок сообщений, возобновление.
- Сериализация действий: одна очередь на сессию — действия desktop и phone исполняются строго
  последовательно.
- Рассылка представлений (`PlayerView` → desktop, `PhoneView` → phone) и событий.
- Выпуск и проверка QR-токенов; генерация QR-матриц.
- Сохранения (автосохранение журнала действий), загрузка.
- Логирование и диагностика.

## 2. Модули

```
apps/server/src/
├── config/        — env: HS_PORT (7420), HS_HOST (0.0.0.0), HS_DATA_DIR, HS_DEBUG_TRUTH, HS_LOG_LEVEL
├── sessions/      — SessionManager, Session (engine, queue, clients, stateVersion, eventBuffer)
├── pairing/       — коды привязки, rate limit, токены устройств (хранятся хеши)
├── gateway/       — WS: hello/auth, роли, heartbeat, seq/ack, resume, маршрутизация сообщений
├── views/         — вычисление и рассылка view.update, фильтр событий по видимости
├── qr/            — payload pairing/evidence, HMAC, матрица QR, реализация EvidenceTokenPort
├── saves/         — запись журнала действий, чекпойнты, загрузка (ADR 0014)
├── diagnostics/   — /health, /debug (только HS_DEBUG_TRUTH), метрики сессии
├── routes/        — GET /scenarios, POST /sessions: каталог сценариев, InvestigationProvider на генераторе
└── app.ts         — сборка Fastify; server.ts — запуск
```

### Конфигурация

Сервер читает переменные окружения перед открытием порта и завершает запуск с ошибкой, если
значение не проходит проверку.

| Переменная | По умолчанию | Допустимые значения |
|------------|--------------|---------------------|
| `HS_PORT` | `7420` | Целое от 1 до 65535 |
| `HS_HOST` | `0.0.0.0` | Непустой адрес привязки или имя хоста |
| `HS_PUBLIC_HOST` | не задан | Конкретный IPv4-адрес или имя хоста без порта (символы `A–Z a–z 0–9 . -`). Адрес `0.0.0.0` допустим для `HS_HOST` и отклоняется здесь при чтении конфигурации. Явный адрес отменяет определение LAN-адреса для QR (выбор адреса — §3, «Создание сессии») |
| `HS_DATA_DIR` | `.hollow-signal` в домашнем каталоге | Непустой путь к каталогу данных |
| `HS_LOG_LEVEL` | `info` | `fatal`, `error`, `warn`, `info`, `debug`, `trace`, `silent` |
| `HS_DEBUG_TRUTH` | `0` | `0` выключает флаг, `1` включает |

Каркас сервера читает `HS_DATA_DIR` и `HS_DEBUG_TRUTH` при старте. С `HS_DEBUG_TRUTH=1` сервер при
запуске пишет предупреждение, а отладочные маршруты (§3, §6) регистрируются; без флага их нет вообще.

## 3. REST API (`/api/v1`)

| Метод и путь | Аутентификация | Тело / ответ | Ошибки |
|--------------|----------------|--------------|--------|
| `GET /health` | — | `{ status, version, protocolVersion }` | — |
| `GET /scenarios` | — | `[{ id, title, durationMinutes }]`: сценарии для игрока; `title` — строка (локаль `ru`) | — |
| `GET /network` | — | `{ candidates: [{ address, interface, recommended, virtual }] }` — LAN-адреса для QR привязки, лучшие первыми; `virtual` — похож на Docker/WSL/VM/VPN (остаётся в списке, но ниже); `recommended` — не более одного; `HS_PUBLIC_HOST` идёт первым. Подробности — [setup.md §6](../development/setup.md) | — |
| `POST /sessions` | — | `{ scenarioId, seed?, locale? }` (`locale` — `ru` по умолчанию или `en`) → 201 `{ sessionId, desktopToken, pairing: { code, expiresAt, qrPayload } }`, `Cache-Control: no-store`. Подробности ниже | `INVALID_MESSAGE` (400; 413 — тело больше лимита, 415 — неподдерживаемый `Content-Type`), `SCENARIO_NOT_FOUND` (404), `GENERATION_UNSOLVABLE` (422), `INTERNAL` (500) |
| `POST /sessions/:id/pairing-code` | desktop | → новый `pairing` | `SESSION_NOT_FOUND` |
| `GET /sessions/:id/pairing-qr` | desktop | → `{ size, modules }` текущего кода привязки (новый не выпускается) | `PAIRING_CODE_INVALID` (404, кода нет), `PAIRING_CODE_EXPIRED` (410) |
| `GET /sessions/:id/evidence-qr/:tokenId` | desktop | → `{ size, modules }` | `QR_INVALID` (404), `QR_EXPIRED` (410), `QR_ALREADY_USED` (409) |

Ответы обоих эндпоинтов QR несут `Cache-Control: no-store`: пока QR на экране, он как пароль. Токен
телефона для них не подходит (`UNAUTHORIZED`).
| `POST /pair` | код привязки | `{ code, deviceName, appVersion, protocolVersion }` → `{ sessionId, deviceToken, wsPath }` | `PAIRING_CODE_INVALID`, `PAIRING_CODE_EXPIRED`, `PAIRING_RATE_LIMITED`, `PROTOCOL_MISMATCH` |
| `DELETE /sessions/:id/device` | desktop | отвязать телефон | |
| `GET /saves` | — (локальный сервер) | `[{ saveId, scenarioId, updatedAt, gameTime }]`, новые первыми. `updatedAt` — ISO-время последней записи, `gameTime` — прошедшие игровые минуты (`null`, если файл метаданных потерян). Повреждённые и посторонние файлы в список не попадают | |
| `POST /saves/:saveId/load` | — | → `{ sessionId, desktopToken, pairing }`; `sessionId` равен `saveId`. Ответ с `Cache-Control: no-store` | `SAVE_NOT_FOUND` (404, в том числе неверный формат id), `SAVE_DESYNC` (422, с `error.atAction`), `ACTION_NOT_AVAILABLE` (409, сессия с этим id ещё идёт или уже загружается), `INTERNAL` (500) |
| `GET /sessions/:id/debug/truth` | desktop + `HS_DEBUG_TRUTH=1` | `{ sessionId, scenarioId, seed, generatorVersion, minute, truth }`: журнал истины целиком | 404 если флаг выключен (маршрута нет); `UNAUTHORIZED`, `SESSION_NOT_FOUND`, 501 если движок сессии нельзя осмотреть |
| `GET /sessions/:id/debug/export` | desktop + `HS_DEBUG_TRUTH=1` | репро-пакет `{ format: "hollow-signal-repro", exportedAt, server, session, scenarioId, seed, generatorVersion, stateHash, snapshot }` | как у `debug/truth` |

Оба отладочных ответа содержат решение: они идут с `Cache-Control: no-store`, а каждое обращение
записывается в лог предупреждением (сессия, без содержимого).

Аутентификация desktop — заголовок `Authorization: Bearer <desktopToken>`. Ошибки — формат
`{ error: { code, message } }`, HTTP 4xx/5xx; у `SAVE_DESYNC` добавлено `atAction`.

Схемы запросов и ответов (кроме `debug/*`) лежат в `@hs/protocol` (`src/rest.ts`), сервер
проверяет ими ответы, а клиенты — фикстуры `fixtures/rest/`; таблица схем —
[protocol.md §4a](protocol.md#4a-rest-схемы).

Приложение регистрирует маршруты при передаче сервиса привязки в buildApp.
При создании сессии SRV-002 выдаёт desktop-токен и первоначальный код через сервис привязки.
expiresAt — Unix-время в миллисекундах. При отзыве сервис удаляет хеш токена и передаёт
DEVICE_REVOKED обработчику шлюза (SRV-004).

### Создание сессии (SRV-002)

Код — `apps/server/src/routes`: `sessions.ts` (маршруты и zod-схемы запроса и ответов),
`generation.ts` (каталог сценариев, провайдер на генераторе, seed, сборка зависимостей для
`server.ts`).

- **Сценарии.** При старте сервер загружает каждый каталог `content/scenarios/<id>`
  (`loadScenarioFromDir`); ошибка контента останавливает запуск. Каталоги с `_` в начале имени
  (`_test_minimal`) — тестовый контент: их нет в `GET /scenarios`, и `POST /sessions` отвечает на
  них `SCENARIO_NOT_FOUND`. Порядок списка — по `id`. `GET` и `POST` проверяют `id` одной схемой
  (`ScenarioId`, 1–64 символа): сценарий, который `POST` не примет (или чья запись списка не проходит
  `ScenarioList`), останавливает запуск, а не появляется в списке.
- **Запрос.** Тело строгое (лишние поля — `INVALID_MESSAGE`). `scenarioId` — строка 1–64 символа.
  `seed` — `[A-Za-z0-9_-]{1,64}`: без `#` (генератор называет попытки `<seed>#<n>`), пробелов и
  управляющих символов, поэтому он безопасен в логе. Отказы Fastify при чтении тела тоже дают
  `INVALID_MESSAGE` со своим статусом: пустой или некорректный JSON и неверный `Content-Length` —
  400, тело больше лимита (1 МБ) — 413, неподдерживаемый `Content-Type` — 415. Тело `text/plain`
  Fastify принимает как строку, его отвергает схема (400). При подготовке сессии только ошибки
  неизвестного сценария и отказа генерации дают 404 и 422 соответственно. Остальные сбои дают
  `INTERNAL` (500), включая отклонение без причины и исключение с полями ошибки парсера. Ответ и
  лог содержат общий код ошибки без текста исключения.
- **Seed по умолчанию.** Без `seed` сервер берёт 12 символов Crockford Base32 из CSPRNG
  (`crypto.randomInt`) и пишет их группами `XXXX-XXXX-XXXX` (60 бит). Сервер проверяет
  автоматически созданный seed той же схемой, что и seed клиента. При нарушении сервер
  возвращает `INTERNAL` до генерации. Seed вместе со сценарием и версией генератора позволяет
  воспроизвести дело по [ADR 0004](../architecture/adr/0004-determinism.md), поэтому поля
  `seed` в ответе о создании сессии нет.
- **Генерация.** `GeneratorInvestigationProvider` реализует `InvestigationProvider` SRV-001 через
  `generateInvestigation` (GEN-011) с полным шлюзом валидации. Отклонённое шлюзом дело — ошибка
  `GENERATION_UNSOLVABLE` (422): провайдер бросает её до того, как `SessionManager` выдаёт id, так
  что ни сессии, ни токена, ни кода привязки не появляется. Текст находок шлюза в ответ не попадает
  (он называет персонажей). Порты движка (`sessions/scenario-ports.ts`, SRV-012) собираются из одного принятого
  результата и пресета: `startLocationId`, `clues`, `testimony.witness` (память и политика лжи
  из `knowledge`/`liePolicies`), `accusation.rules`, `startVitals` пресета и `phone.initial`
  (`initialPhoneState` из шаблонов). SRV-010 добавляет `texts`: все группы `text/ru/*.json`
  объединяются в карту `TextTemplates`. Общий провайдер используется как при создании, так и при
  регенерации сохранения, поэтому реплики NPC проецируются на русском и после загрузки. `actionCosts`, `player`, `inventory` и арбитраж звонка —
  значения движка. `$incident` берётся из сведений игрока: `AccusationPort.incident` может быть
  функцией от `PlayerKnowledge` (OQ-25). Порты не покидают процесс сервера.
  Генерация синхронная (сотни миллисекунд на `sanatorium_winter`) и на это время занимает поток
  сервера.
- **Атомарность подготовки.** `SessionManager.create` регистрирует сессию после синхронного
  `prepare`, который выпускает desktop-токен, код привязки и проверяет DTO. ID зарезервирован
  на время подготовки, чтобы `adopt` не опубликовал другой объект с тем же ID. При сбое подготовки
  маршрут стирает хеш, удаляет принадлежащий этой сессии код из обеих таблиц и отвечает
  `INTERNAL` (500). При ошибочной передаче Promise менеджер отклоняет создание и обрабатывает
  возможное отклонение Promise. За внешнее состояние отвечает callback. Сериализация и
  доставка HTTP-ответа происходят после регистрации. При их сбое готовая сессия может остаться
  на сервере.
- **Адрес QR привязки.** Сервер использует `HS_PUBLIC_HOST` или явный `HS_HOST` в виде IPv4-адреса
  или имени без порта. Интерфейсы перебираются только при wildcard bind `0.0.0.0` или `::`.
  Выбирается первый LAN-кандидат, а при пустом списке используется локальный `127.0.0.1`.
  Для `::` этот путь предполагает, что системный сокет принимает IPv4. При привязке к
  конкретному IPv6-адресу подготовка сессии требует `HS_PUBLIC_HOST` с доступным телефону
  адресом или именем. Без него подготовка заканчивается `500 INTERNAL` без регистрации
  сессии. За доступность явно заданного публичного адреса отвечает конфигурация установки.
  Формат `hs1:pair:<host>:<port>:<code>` по ADR 0008 допускает IPv4 или имя, порт 1–65535 и
  код, совпадающий с `pairing.code`. Поддержка литералов IPv6 требует решения по протоколу.
  `GET /network` (SRV-008) по-прежнему перечисляет все интерфейсы, поэтому при явном bind его
  рекомендация может отличаться от адреса в pairing payload.
- **Ответ.** 201 `{ sessionId, desktopToken, pairing }`. `sessionId` — UUID v4,
  `desktopToken` — 256 бит base64url (в сессии хранится только SHA-256), `pairing` — как у
  `POST /sessions/:id/pairing-code`. Статус новой сессии — `created`; активирует её привязка
  телефона. Истины в ответе нет: ни персонажей, ни виновника.
- **Схемы.** `CreateSessionRequest`, `CreateSessionResponse`, `ScenarioList` и `ErrorResponse`
  (с `ErrorCode` из `@hs/protocol`) экспортирует `routes/sessions.ts`. Ответ `POST /sessions`
  проверяется схемой и на production-пути до регистрации сессии, остальные — в integration-тестах.
  В `@hs/protocol` схем REST пока нет ([PROTO-006](../../tasks/PROTO-006.md)).
- **Проверка полного шлюза.** Интеграционный тест через `createSessionServices` проверяет,
  что на копии `_test_minimal` без правил дедукции полный шлюз отклоняет дело, которое прошло
  бы при `checks: []`. Проверка штатного HTTP 201 использует решаемый seed публичного сценария
  и полный шлюз.

### Сохранения ([ADR 0014](../architecture/adr/0014-save-system.md))

Код — `apps/server/src/saves`. Формат и replay — `@hs/core/save` (SAVE-001); сервер только пишет и читает файлы.

- **Файлы.** `HS_DATA_DIR/saves/<sessionId>.json` (журнал) и рядом `<sessionId>.meta.json`
  (`{ gameTime }` для списка: производные данные, не источник истины). Идентификатор — только
  `[A-Za-z0-9_-]{1,64}`, иначе это не сохранение (защита от выхода из каталога). Файлы создаются с
  правами `0600` (в них истина), каталог — `0700`.
- **Публичный список.** Для активных и завершённых дел `GET /saves` возвращает одинаковый
  набор метаданных. Seed хранится в журнале для загрузки и replay. После завершения дела
  seed доступен игроку в `EndingView.seed`. [ADR 0023](../architecture/adr/0023-save-list-seed.md)
- **Автосохранение.** `SaveService.createEngine` передаётся в `SessionManager` и оборачивает
  `GameEngine`: каждое действие идёт через `recordAction`, затем журнал целиком записывается на диск и
  только после этого результат уходит клиенту. Каждое 50-е действие добавляет чекпойнт (это делает
  `recordAction`). До первого действия ничего не пишется. Отклонённые движком действия тоже попадают в журнал (состояние не меняется).
- **Атомарность.** Запись идёт во временный файл `<имя>.<hex>.tmp` в том же каталоге
  (`open wx`, `fsync`), затем `rename` поверх цели. Обрыв оставляет прежний файл целым; временные
  файлы список не видит, а при старте (`onReady`) сервер их удаляет. Сначала пишется журнал, потом
  метаданные: при обрыве между ними `gameTime` отстаёт на одно действие.
- **Сбой записи** (диск, права) переводит сессию в `faulted` (`INTERNAL`): на диске остаётся последнее
  согласованное состояние, в памяти — на одно действие впереди, продолжать нельзя.
- **Загрузка.** `POST /saves/:id/load` регенерирует расследование через тот же `InvestigationProvider`,
  вызывает `loadSave` (цепочка хешей, чекпойнт + хвост, `finalStateHash`) и отказывает с `SAVE_DESYNC`,
  если версия генератора не совпала. Ответ HTTP 422 содержит `atAction: 0` и обе версии в
  `error.message`. Файл остаётся на диске. Политика описана в
  [ADR 0019](../architecture/adr/0019-save-generator-compatibility.md). При успехе создаётся сессия с `sessionId = saveId`
  (дальнейшие действия дописываются в тот же файл: одно сохранение на прохождение), выдаются новый
  desktop-токен и код привязки; статус сессии `created`, телефон привязывается заново. Если сессия с
  этим id ещё идёт (`created`/`active`), загрузка отклоняется (409). Загрузка может заменить
  приостановленную, завершённую, сбойную или удалённую по TTL сессию.
- **Смена сессии при загрузке (SRV-014).** Менеджер резервирует `saveId` на время загрузки.
  Второй запрос с тем же ID получает 409. При замене чтение журнала ждёт завершения уже
  поставленных в очередь действий и их записей. Восстановленный движок, desktop-токен, код
  привязки и проверенный DTO готовятся до фиксации. Затем в одном синхронном шаге менеджер
  публикует сессию, право записи переходит к новому движку, а старые токены и код отзываются.
  Если подготовка завершается ошибкой, прежняя сессия, её credentials и право записи сохраняются.
  Неожиданный сбой возвращает `500 INTERNAL`, в ответ и журнал попадает только безопасное
  описание. Сериализация и доставка HTTP-ответа происходят после фиксации.
- **Не сохраняется** состояние порта улик (выпущенные QR-токены): оно живёт в памяти процесса и
  определяется провайдером; после загрузки ожидающий скан токен нужно выпустить заново.
- Лог: имена файлов и содержимое сохранений не пишутся; ответы `/saves` не содержат токенов и истины.

## 4. Жизненный цикл сессии

```
created → (pairing) → active → (game over) → finished → (TTL 30 мин без клиентов) → disposed
                    ↘ suspended (desktop отключился > 60 с) → active (переподключение)
```

- Создание: генерация расследования (до 8 попыток; > 2 с — предупреждение в логе).
- Сессия хранит: `engine`, `actionQueue`, `stateVersion`, `eventSeq`, кольцевой буфер последних
  200 событий, токены (хеши), выпущенные QR-токены, привязку устройства.
- Действия исполняются по одному; при ошибке движка сессия помечается `faulted`, сохранение
  сохраняется, клиенты получают `INTERNAL` — это баг, а не игровое состояние.

- `SessionManager.create(scenarioId, seed)` получает расследование и входные порты движка
  через `InvestigationProvider`. Активация, подключение клиентов, действия и проверка
  TTL используют одну очередь сессии. Время TTL измеряется сервером в реальных
  миллисекундах, игровые минуты продвигает движок при действии.
- Успешное действие увеличивает `stateVersion`. События получают последовательные
  номера. Если запрошенный номер старше буфера, `eventsAfter` возвращает `null`
  для полной синхронизации. `sweep` освобождает завершённые сессии после TTL.

## 5. Отключения и переподключения

- Heartbeat: клиент шлёт `ping` каждые 10 с; нет сообщений 30 с — соединение закрывается.
- Переподключение: `hello { role, token, resume: { lastSeq, stateVersion } }`. Если `lastSeq` в
  буфере — досылаются пропущенные события + актуальный `view.update`; иначе `resync` (полный снимок).
- Отключение телефона во время игры: игра не останавливается автоматически (время идёт только
  от действий), но Godot показывает статус «телефон отключён»; действия, требующие телефона, недоступны.
- Отключение desktop: сессия `suspended`, данные не теряются (автосохранение).

## 6. Логирование

- Каркас пишет HTTP-метод, шаблон маршрута, статус и время ответа. Параметры URL, заголовки и тела
  запросов в эту запись не попадают. Для маршрутов сессии добавляется `sessionId` (только если значение
  имеет формат UUID).
- Сбой сервера (исключение без статуса или статус ≥ 500) пишется отдельной записью `request failed`
  уровня `error` с кодом `INTERNAL`. Текст исключения и стек могут содержать секреты и пропускаются.
  Отказы, вызванные клиентом (401,
  404, ошибки валидации), отдельной записи не получают: они видны статусом в строке ответа.
- pino JSON; поля: `sessionId`, `role`, `msgType`, `durationMs`. **Токены, коды и содержимое истины не
  логируются никогда**, в том числе при `HS_DEBUG_TRUTH=1`: отладочная истина отдаётся только ответом
  эндпоинта. Второй рубеж: pino заменяет на `[redacted]` значения полей `authorization`, `cookie`,
  `token`, `tokenId`, `deviceToken`, `desktopToken`, `pairingCode`, `sig`, `signature`, `secret`,
  `sessionSecret`, `password`, `raw`, `qrPayload` на любой глубине (до двух уровней вложенности), если
  кто-то залогирует объект с такими полями.
- Генерация логирует `seed`, `generatorVersion`, попытки, время стадий: запись `generation finished`
  (`info`) или `slow generation` (`warn`, дольше 2 с) с полями `scenarioId`, `seed`,
  `generatorVersion`, `ok`, `attempts`, `durationMs`, `stageMs` (сумма по попыткам) и `rejections`
  — только коды отказов (`INCIDENT_NO_FEASIBLE_CULPRIT`, `V-UNIQUE:NOT_UNIQUE`), как `hs-gen` без
  `--debug-truth`. Тексты находок и выбранный инцидент называют персонажей и в лог не пишутся.

### Отладка и репро

- `GET /sessions/:id/debug/truth` и `GET /sessions/:id/debug/export` существуют только при
  `HS_DEBUG_TRUTH=1` и только для токена desktop. Без флага маршрутов нет, и ответ неотличим от
  ответа на любой неизвестный путь (404), в том числе для верного токена. Флага недостаточно: маршруты
  регистрируются, только если приложению переданы зависимости диагностики. В релизных сборках флаг
  должен игнорироваться ([truth-model.md §6](../investigation/truth-model.md)): это забота упаковки
  (INT-005), здесь признака релиза нет.
- **Экспорт репро** как команда: `HS_DESKTOP_TOKEN=<desktopToken> npm run export-repro -w @hs/server --
  <sessionId> [--url http://127.0.0.1:7420] [--out repro.json]`. Токен берётся только из окружения
  (командная строка видна другим процессам и попадает в историю оболочки), файл создаётся с правами
  `0600` на POSIX, потому что содержит решение. На Windows файл наследует ACL каталога назначения.
  `desktopToken` возвращает `POST /sessions`.
- Репро-пакет содержит снимок движка (сериализованное расследование вместе с истиной, минуту, локацию),
  хеш состояния, `seed`, `scenarioId`, `generatorVersion` и версии сервера и протокола.
  `GameEngine.restore(bundle.snapshot, investigation, ports)` даёт то же состояние (проверяется тестом).
  Истории действий в пакете пока нет: её добавит формат сохранения (SAVE-001).

## 7. Тесты

- Fastify `inject` для REST; реальные `ws`-клиенты на случайном порту для WS-сценариев.
- Сценарии: создание сессии → привязка → hello обеих ролей → действие → оба получили `view.update`;
  неверный/просроченный/повторный код; rate limit; resume с буфером и без; повторный QR;
  QR чужой сессии; одновременные действия desktop и phone сериализуются.

### Реальные проекции и события (SRV-010)

`SessionGateway` по умолчанию читает `Session.engine.playerView()` / `phoneView()`;
`RecordingEngine` делегирует эти методы движку сохранения. Тестовые движки без методов проекции
не публикуют снимок. Кэш и проверка схем по роли сохраняются. Штатная фабрика передаёт этому шлюзу тот же менеджер сессий,
который обслуживает REST и привязку (SRV-013).

`engineEvents` использует разрешённый список: уведомления, входящие звонки и успешная фиксация
улики адресуются только телефону, с проверкой ссылки в реальной проекции. Исходные объекты
доменных событий не сериализуются; остальные изменения доступны через полный снимок.
`gameOver` шлюз отправляет обеим ролям по исходу действия. Подробности — [protocol.md §7](protocol.md#7-последовательности).

### Штатная сборка с WebSocket и QR (SRV-013)

`createSessionServices(config, { scenariosDir?, networkInterfaces? })` возвращает зависимости
для `buildApp`: `sessions`, `pairing`, `gateway` и `qr`. Этот же вход использует нативный
`node src/server.ts` (`npm start -w @hs/server`). Явный `scenariosDir` позволяет упаковщику
передать собственный каталог контента; полный шлюз генерации остаётся включён.

Фабрика создаёт отдельный `EvidenceTokenStore` для каждого движка и передаёт его в
`EnginePorts.evidenceTokens`. В синхронном `SessionRouteDependencies.prepare(session)`
хранилище привязывается к созданной сессии до выдачи токенов и регистрации в менеджере.
`QrService` берёт игровые минуты из движка, а маршруты матриц используют desktop-авторизацию
и текущий код `PairingService`.

После первого успешного `qr.scan` сервис помечает токен использованным и передаёт точный
`SessionDispatchResult` в callback `onCaptured`. `buildApp` направляет его в
`SessionGateway.publishDispatch`: обе роли получают снимки с версией этого действия,
phone — видимый `scanResult`, при исходе обе роли — `gameOver`. Рассылка происходит до
ответа `qr.result`; клиент обрабатывает сообщения по их типу. Повторный или чужой скан
не вызывает callback, не тратит время и не создаёт новую версию или повторную рассылку.
Сохранения и присоединение загруженной игры к фабрике остаются SRV-014/015.
