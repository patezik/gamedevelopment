# Конвейер процедурной генерации расследования

Решение — [ADR 0006](../architecture/adr/0006-generation-pipeline.md). Код — `@hs/generator`.

## 1. Принцип

Сначала создаётся **мир с людьми**, затем в этом мире выясняется, **кто мог** совершить
преступление, и лишь затем выбирается, **кто совершил**. Улики и показания не придумываются
отдельно — они следуют из событий истины и знаний персонажей.

## 2. Стадии

Каждая стадия — чистая функция `(input, ctx) → output` с собственным подпотоком
`ctx.rng = root.fork("gen/<stage>")` ([ADR 0004](../architecture/adr/0004-determinism.md)).

`runPipeline(stages, input, options)` связывает типы входа и выхода соседних стадий.
Первая попытка использует `<seed>#1`, последующие — `<seed>#N`. Предикат `accepts`
позволяет шлюзу валидации отклонить результат и запустить следующую попытку.
Стадия, для входа которой нет допустимого результата, бросает `GenerationRejection(code, message,
diagnostics?)`: попытка записывается как отклонённая (`accepted: false`, `rejection: { stage, code,
message, diagnostics? }`), следующие стадии и `accepts` не запускаются, начинается следующая
попытка. Любое другое исключение — дефект и пробрасывается. Если отклонены все `maxAttempts`
попыток — `GENERATION_UNSOLVABLE`.
Отчёт хранит seed и длительность каждой стадии для каждой попытки. Замеры времени
поступают из переданной функции `now`, используются для диагностики и не входят в расследование.

| # | Стадия | Вход | Выход | Ключевые правила |
|---|--------|------|-------|------------------|
| 1 | **WorldGen** | пресет | `GeneratedWorld` с графом и `createWorldState` | Варианты из пресета (какие комнаты заперты, где лежат предметы) |
| 2 | **CastGen** | пресет, мир | `Character[]` | Архетипы по квотам пресета; личность — сэмпл распределений архетипа; имена из пулов; биографии из тегированных фрагментов |
| 3 | **SocialGen** | персонажи | `SocialWorld`: персонажи с секретами, `RelationshipGraph`, `SocialSecret[]`, события предыстории | Шаблоны отношений (родство, роман, долг, вражда, служебные); один супруг, родитель старше на 16–60 лет; у каждого ≥ 2 партнёра и ≥ 1 секрет; правила — [scenario-presets.md §6](scenario-presets.md#relationshipsjson-и-стадия-socialgen) |
| 4 | **ConflictGen** | `SocialWorld` | `ConflictWorld`: `SocialWorld` + `MotiveCandidate[]` для всех упорядоченных пар, `MotiveReport`, события мотивов в предыстории | Правила `motives.json`: условие на отношения/секреты → тип и сила мотива; см. ниже |

| 6 | **PlotPlanning** | план, расписания | действия виновника (подготовка, подход, деяние, сокрытие, алиби) | Окно возможности встраивается в расписание; если нужно — расписание «изгибается» правдоподобной причиной |

| 8 | **EvidenceGen** | журнал, правила следов | `Trace[]`, `Clue[]` | `TraceRule` по глаголам; закон сохранения улик; распределение `captureMode` |
| 9 | **TestimonyGen** | знания, секреты | `LiePolicy` каждого, банк тем | Ложь только при мотиве скрывать |
| 10 | **RedHerrings** | секреты невиновных | дополнительные следы их (реальных) проступков | Это истинные события, не фальшивки |

WorldGen проверяет достижимость из старта по направленным связям, считая доступными все
существующие ключи. Доступность по времени и фактическое получение ключей проверяются при
валидации расследования. После CastGen вызывающий код передаёт отображение «архетип → ID
владельца» в `createWorldState`, чтобы создать реестр предметов с начала предыстории.

### ConflictGen

ConflictGen проверяет каждое правило `motives.json` для каждой упорядоченной пары `(c, v)`, `c ≠ v`,
и не использует случайность: результат не зависит от подпотока и порядка правил и персонажей.
В правиле `$c` — тот, у кого мотив, `$v` — против кого; других переменных и литеральных
идентификаторов нет. Условия `when`:

- `relation { type, from, to }` — ребро `from → to` типа `type` есть в `RelationshipGraph` с учётом
  обратных рёбер. Поэтому `child $c → $v` и `parent $v → $c` — одно условие («`c` — ребёнок `v`»),
  а симметричные типы (`spouse`, `sibling`, …) совпадают в обе стороны. `debt`, `employment` и
  `blackmail` направлены: обратного прочтения нет;
- `secret { kind, about, knownBy }` — есть секрет вида `kind` о `about`, который знает `knownBy`
  (исходные `knownBy` SocialGen);
- оба условия должны выполняться; `when` без условий — ошибка, иначе у мотива не было бы основания.

Сила — `base` плюс `add` каждого бонуса, условие которого выполнено: `trait` вида `$c.<черта>`
или `$v.<черта>`, `lt` и/или `gt` (оба — диапазон). Сумма ограничивается `[0, 1]` и округляется
до 6 знаков. Неизвестные тип отношения, переменная или черта, условие без границ или пустой
диапазон, повторный `id` правила — `RangeError`.

`MotiveCandidate { who, against, motiveType, strength, basis }`: `motiveType` — `id` правила,
`basis` — отсортированные `FactId` факта `relation` ребра (из события в `Relationship.history`) и
фактов `state` совпавших секретов. Кандидаты отсортированы по `who`, `against`, `motiveType`.
Кандидат с силой `≥ preset.incident.minMotive` (тот же порог, что в §3) становится фактом
`motive` (`motiveFact(candidate)`) в событии `harbor_motive` (`private`, без акторов, цели — оба
персонажа). Событие добавляется после событий SocialGen с продолжением нумерации `ev_N`; его
`causes` — события фактов `basis`, время и локация — последнего из них. Если во входе уже есть
факты `motive`, стадия выбрасывает ошибку вместо дублирования.

`MotiveReport` — серверная диагностика, не попадает в представления клиентов: число проверенных
пар и правил, кандидатов, кандидатов не ниже порога, пар с мотивом, персонажей с мотивом,
гистограмма силы по 10 интервалам `[i/10, (i+1)/10)` и статистика по каждому правилу.
ConflictGen не выбирает жертву и виновника — это IncidentSelection (§3).

Ограничение MVP: CastGen задаёт всем персонажам возраст 45, поэтому в санатории нет рёбер
`parent`/`child` и правило `inheritance` не срабатывает. На сидах 0–199 с текущим `motives.json`
кандидатов нет в 32 мирах (16 %): в них IncidentSelection не найдёт виновника с мотивом
не ниже порога (§3).

## 3. Выбор виновника (IncidentSelection)

```
victimCandidates = персонажи, удовлетворяющие ограничениям пресета на жертву
для каждой жертвы v (взвешенно по «заметности» и числу мотивов против неё):
  для каждого шаблона преступления T, разрешённого пресетом:
    feasible = []
    для каждого персонажа c ≠ v (ВСЕ участники мира, не список подозреваемых):
      motive  = max силы MotiveCandidate(c → v)               ≥ preset.minMotive
      means   = доступ c к средству T (access grants, локации, предметы) или способ получить
      opport  = в расписании c найдётся окно ≥ T.minWindow в локации, доступной для T,
                которое можно сделать «без свидетелей» изгибом не более 1 блока расписания
      capable = требования T к личности/физическим данным (например, impulsivity для «удара»)
      если всё выполнено → feasible.push({ c, score = motive · w1 + opportunityQuality · w2 + personalityFit · w3 })
    если feasible не пусто → выбрать c = rng.weighted(feasible по score^γ) ; γ = 0.7 сглаживает доминирование
```

Свойства: (1) нет заранее заданных подозреваемых; (2) любой персонаж, у которого в этом мире
сложились мотив, средства и возможность, может стать виновником; (3) параметр `γ` и пороги
контролируются seed sweep по энтропии распределения виновников.

### Реализация (GEN-006)

Вход стадии — `IncidentSelectionInput`: `ConflictWorld` и `world` (`GeneratedWorld` WorldGen).
CastGen не передаёт мир дальше, поэтому вызывающий код добавляет его к выходу ConflictGen.
Стадия — это `assessIncidents` (оценка) и `selectIncident` (выбор на готовой оценке).

**Мир и владельцы.** Предметы с `ownerArchetype` (с учётом выбранного варианта мира) получают
владельца — первого по id персонажа архетипа. Если архетипа владельца нет в составе, мир нельзя
создать (у предмета нет начального размещения): стадия бросает `GenerationRejection` с кодом
`WORLD_OWNER_ABSENT`, и конвейер перегенерирует мир (§2). Остальные ошибки данных
(`ItemError`, `RangeError`) не перехватываются.

**Присутствие — по симуляции.** Оценка один раз прогоняет распорядки всего состава через
`SimulationRunner` от `historyStartMinutes` до `t = 0` — так же, как HistorySimulation:
персонажи идут шаг за шагом по `LocationGraph.nextTimedStep`, ждут открытия по часам доступа,
проходят только двери, ключи от которых несут, и между локациями находятся в пути (`in_transit`).
«Находится в локации» везде ниже — факт `at` этого прогона, а не плановое место по распорядку.

**Оценка выполнимости** — `assessIncidents(input, content)`; от случайности результат не зависит
(подпоток прогона влияет только на восприятие, которое не используется). Жертвы — персонажи,
чей архетип не входит в `victimConstraints.excludeArchetypes`; шаблоны — из
`preset.incident.templates` с `incidentType` из `types` (чтение полей шаблона —
[scenario-presets.md §4](scenario-presets.md#4-шаблон-преступления-crimesjson)). Для каждой пары
(жертва, шаблон) проверяется **каждый** персонаж, кроме жертвы. Критерии проверяются по порядку,
первый невыполненный учитывается в `rejected`:

1. **motive** — самый сильный `MotiveCandidate(c → v)` не ниже `minMotive`; при равенстве силы —
   меньший `motiveType`.
2. **capable** — личность `c` строго внутри всех границ `requires.traits`.
3. **means** — предмет с тегом (и `itemId`, если задан), который `c` может получить до `t = 0`:
   несёт его с начала предыстории; оказывается в его локации; оказывается в одной локации с его
   владельцем (по распорядку или изменив один блок, см. ниже).
4. **opportunity** — существует совместимая пара «средство — окно»: окно
   `[s, s + minWindowMinutes)` целиком в предыстории в локации со всеми тегами `locationTags`
   (сцена), и всё это время:
   - `c` в сцене, уже держа это средство (взятое не позже минуты `s − 1`);
   - никого другого в сцене нет — спящий тоже свидетель, потому что `SimulationRunner.observe`
     учитывает всех присутствующих; жертва не свидетель, если план направлен на неё;
   - если в плане есть шаг с `target: "$victim"`, жертва в сцене;
   - смерть наступает до начала расследования: при `deathDelayMinutes = [min, max]` есть минута
     `d` в `[s + minWindowMinutes + min, s + minWindowMinutes + max]`, `d < 0`; если в плане нет
     шага на жертву, в минуту `d` жертва находится в сцене.

**Как виновник оказывается в сцене.** Либо распорядок сам держит его в сцене всё окно, а средство
у него уже есть («без изгиба»), либо меняется **один** блок распорядка — одно вхождение блока
`[b0, b1)`. Изменение начинается в минуту `o0 ∈ [b0, b1)` там, где `c` физически находится
минутой раньше (в начале предыстории — в стартовой локации; в пути начинать нельзя), и длится до
конца окна, `s + minWindowMinutes ≤ b1`. В нём `c` идёт за средством (в его локацию или туда, где
в это время его владелец; на месте — одна минута), затем в сцену. Маршрут — пошагово через
`nextTimedStep` с учётом часов доступа всех промежуточных локаций. Ключи от средства действуют
только после того, как оно взято. Если `c` уже в сцене, когда изменение начинается, окно может
начаться раньше `o0`, пока его держит в сцене распорядок. Каждое средство рассматривается
отдельно: время одного и ключи другого не объединяются.

**Проверка симуляцией.** Отсев по базовому прогону не учитывает, что взятое средство меняет мир:
ключ открывает виновнику маршруты (и его распорядок может увести его из сцены), а владелец без
ключа больше не проходит свои двери. Поэтому для каждой сцены первые
`VERIFIED_WINDOWS_PER_SCENE` (3) окна по времени проверяются повторным прогоном
`SimulationRunner`: изменённый блок задаётся `ScheduleOverride` (до места получения, затем до
сцены), средство переходит к `c` в `ItemRegistry` в минуту после получения. Окно принимается,
если в этом прогоне выполнены все условия выше. Первое подтверждённое окно попадает в
`opportunities`; отклонённые считает `windowsRejectedBySimulation`.

**Оценка кандидата.** `score = 0,5 · motive + 0,3 · opportunityQuality + 0,2 · personalityFit`
(`SCORE_WEIGHTS`), `score ∈ (0, 1]`, округление до 6 знаков.
`opportunityQuality = min(1, число допустимых начал окна по всем сценам / 60)`
(`OPPORTUNITY_SATURATION_MINUTES`; начала считаются по базовому прогону); `personalityFit` —
средняя глубина внутри границ черт (`(x − gt) / (1 − gt)`, `(lt − x) / lt`), 1 без требований.

**Выбор** (`selectIncident`). Подпотоки `ctx.rng` (`gen/IncidentSelection`):

- `victim` — порядок жертв: взвешенный выбор без возвращения, вес
  `(1 + число партнёров по отношениям) · (1 + число мотивов против неё не ниже порога)`;
- `template/<victimId>` — случайный порядок шаблонов для жертвы;
- `culprit/<victimId>/<templateId>` — для первого шаблона с непустым `feasible`:
  `rng.weighted(feasible, score^γ)`, `γ = preset.incident.gamma ?? 0,7` (`DEFAULT_CULPRIT_GAMMA`).

Результат не зависит от порядка персонажей и мотивов во входе. Если ни для одной пары
(жертва, шаблон) нет допустимого виновника, стадия бросает `GenerationRejection` с кодом
`INCIDENT_NO_FEASIBLE_CULPRIT` и `diagnostics.incidentReport`, и конвейер начинает следующую
попытку (§2).

**Выход** — `IncidentWorld`: вход и

- `incident: IncidentPlan { type, templateId, victimId, culpritId, motive, meansItemIds,
  opportunities, score }`. `opportunities` — по одному подтверждённому самому раннему окну в
  каждой сцене: `{ locationId, from, to, starts, meansItemId, acquisition, deviation, deathAt? }`;
  `acquisition { locationId, at, fromCharacterId? }` — где и когда взято средство (`null`, если
  оно у виновника с начала); `deviation { from, to }` — изменённый блок (`null` без изгиба).
  Это пример выполнимого плана; точные шаги, причину изгиба и алиби строит PlotPlanning (GEN-007);
- `incidentReport: IncidentReport { gamma, victimsEligible, feasibleCulpritCount,
  feasibleTriples, byTemplate, rejected, windowsRejectedBySimulation, chosen }`:
  `feasibleCulpritCount` — число допустимых виновников для выбранных жертвы и шаблона;
  `byTemplate[T]` — жертвы с допустимым виновником, пары (жертва, виновник) и различные виновники
  шаблона `T`; `rejected` — отказы по первому невыполненному критерию. Это истина сервера,
  не для клиентов.

Для seed sweep (например, проверки выполнимости шаблонов сценария) `assessIncidents` выдаёт по
каждому шаблону всех допустимых виновников для всех жертв сгенерированного мира без выбора.

Ограничения MVP:

- окно и смерть — только в предыстории (`t < 0`);
- взятое средство остаётся у виновника: возврат ключа или сокрытие (`conceal`) не моделируются,
  поэтому кража единственного ключа может навсегда закрыть владельцу его локацию;
- получение средства занимает одну минуту на месте; длительности шагов плана и их порядок
  проверяет PlotPlanning (GEN-007);
- окно не может продолжаться после конца изменённого блока, даже если следующий блок распорядка
  снова в сцене;
- после отсева проверяются только 3 самых ранних окна на сцену; если взятый ключ меняет
  маршруты, более позднее подходящее окно может быть не найдено (оценка остаётся корректной, но
  неполной);
- свидетели и жертва своих распорядков не меняют; влияние присутствия виновника на других
  персонажей (кроме перемещения средства) не моделируется.

## 4. Отчёт генерации

`GenerationReport { seed, generatorVersion, attempts: AttemptReport[], timingsMs: Record<stage, number>,
feasibleCulpritCount, chosen: { victimArchetype, culpritArchetype, template, motiveType } }` —
**не** отдаётся клиентам (содержит истину), сохраняется в отчётах sweep и debug-логах.
Сейчас `runPipeline` заполняет `seed`, `generatorVersion` и `attempts` (с `rejection` отклонённых
попыток); `feasibleCulpritCount` и `chosen` выдаёт IncidentSelection в `IncidentReport`, их перенос
в `GenerationReport` — задача стадии Packaging.

## 5. Расширяемость

- Новый сценарий = новый пресет (данные). Если пресету нужна новая механика (новый глагол, тип
  следа, тип мотива) — она добавляется в словари ядра отдельной задачей, а не в пресет.
- Новая стадия добавляется в список стадий с собственным подпотоком; существующие результаты
  не меняются, но `GENERATOR_VERSION` увеличивается.
