# Конвейер процедурной генерации расследования

Решение — [ADR 0006](../architecture/adr/0006-generation-pipeline.md). Код — `@hs/generator`.

## 1. Принцип

Сначала создаётся **мир с людьми**, затем в этом мире выясняется, **кто мог** совершить
преступление, и лишь затем выбирается, **кто совершил**. Улики и показания не придумываются
отдельно — они следуют из событий истины и знаний персонажей.

## 2. Стадии

Каждая стадия — чистая функция `(input, ctx) → output` с собственным подпотоком
`ctx.rng = root.fork("gen/<stage>")` ([ADR 0004](../architecture/adr/0004-determinism.md)).

`runPipeline(stages, input, options)` связывает типы входа и выхода соседних стадий.
Первая попытка использует `<seed>#1`, последующие — `<seed>#N`. Предикат `accepts`
позволяет шлюзу валидации отклонить результат и запустить следующую попытку.
Стадия, для входа которой нет допустимого результата, бросает `GenerationRejection(code, message,
diagnostics?)`: попытка записывается как отклонённая (`accepted: false`, `rejection: { stage, code,
message, diagnostics? }`), следующие стадии и `accepts` не запускаются, начинается следующая
попытка. Любое другое исключение — дефект и пробрасывается. Если отклонены все `maxAttempts`
попыток — `GENERATION_UNSOLVABLE`.
Отчёт хранит seed и длительность каждой стадии для каждой попытки. Замеры времени
поступают из переданной функции `now`, используются для диагностики и не входят в расследование.

WorldGen проверяет достижимость из старта по направленным связям, считая доступными все
существующие ключи. Доступность по времени и фактическое получение ключей проверяются при
валидации расследования. После CastGen вызывающий код передаёт отображение «архетип → ID
владельца» в `createWorldState`, чтобы создать реестр предметов с начала предыстории.

### ConflictGen

ConflictGen проверяет каждое правило `motives.json` для каждой упорядоченной пары `(c, v)`, `c ≠ v`,
и не использует случайность: результат не зависит от подпотока и порядка правил и персонажей.
В правиле `$c` — тот, у кого мотив, `$v` — против кого; других переменных и литеральных
идентификаторов нет. Условия `when`:

- `relation { type, from, to }` — ребро `from → to` типа `type` есть в `RelationshipGraph` с учётом
  обратных рёбер. Поэтому `child $c → $v` и `parent $v → $c` — одно условие («`c` — ребёнок `v`»),
  а симметричные типы (`spouse`, `sibling`, …) совпадают в обе стороны. `debt`, `employment` и
  `blackmail` направлены: обратного прочтения нет;
- `secret { kind, about, knownBy }` — есть секрет вида `kind` о `about`, который знает `knownBy`
  (исходные `knownBy` SocialGen);
- оба условия должны выполняться; `when` без условий — ошибка, иначе у мотива не было бы основания.

Сила — `base` плюс `add` каждого бонуса, условие которого выполнено: `trait` вида `$c.<черта>`
или `$v.<черта>`, `lt` и/или `gt` (оба — диапазон). Сумма ограничивается `[0, 1]` и округляется
до 6 знаков. Неизвестные тип отношения, переменная или черта, условие без границ или пустой
диапазон, повторный `id` правила — `RangeError`.

`MotiveCandidate { who, against, motiveType, strength, basis }`: `motiveType` — `id` правила,
`basis` — отсортированные `FactId` факта `relation` ребра (из события в `Relationship.history`) и
фактов `state` совпавших секретов. Кандидаты отсортированы по `who`, `against`, `motiveType`.
Кандидат с силой `≥ preset.incident.minMotive` (тот же порог, что в §3) становится фактом
`motive` (`motiveFact(candidate)`) в событии `harbor_motive` (`private`, без акторов, цели — оба
персонажа). Событие добавляется после событий SocialGen с продолжением нумерации `ev_N`; его
`causes` — события фактов `basis`, время и локация — последнего из них. Если во входе уже есть
факты `motive`, стадия выбрасывает ошибку вместо дублирования.

`MotiveReport` — серверная диагностика, не попадает в представления клиентов: число проверенных
пар и правил, кандидатов, кандидатов не ниже порога, пар с мотивом, персонажей с мотивом,
гистограмма силы по 10 интервалам `[i/10, (i+1)/10)` и статистика по каждому правилу.
ConflictGen не выбирает жертву и виновника — это IncidentSelection (§3).

Ограничение MVP: CastGen задаёт всем персонажам возраст 45, поэтому в санатории нет рёбер
`parent`/`child` и правило `inheritance` не срабатывает. На сидах 0–199 с текущим `motives.json`
кандидатов нет в 32 мирах (16 %): в них IncidentSelection не найдёт виновника с мотивом
не ниже порога (§3).

## 3. Выбор виновника (IncidentSelection)

```
victimCandidates = персонажи, удовлетворяющие ограничениям пресета на жертву
для каждой жертвы v (взвешенно по «заметности» и числу мотивов против неё):
  для каждого шаблона преступления T, разрешённого пресетом:
    feasible = []
    для каждого персонажа c ≠ v (ВСЕ участники мира, не список подозреваемых):
      motive  = max силы MotiveCandidate(c → v)               ≥ preset.minMotive
      means   = доступ c к средству T (access grants, локации, предметы) или способ получить
      opport  = в расписании c найдётся окно ≥ T.minWindow в локации, доступной для T,
                которое можно сделать «без свидетелей» изгибом не более 1 блока расписания
      capable = требования T к личности/физическим данным (например, impulsivity для «удара»)
      если всё выполнено → feasible.push({ c, score = motive · w1 + opportunityQuality · w2 + personalityFit · w3 })
    если feasible не пусто → выбрать c = rng.weighted(feasible по score^γ) ; γ = 0.7 сглаживает доминирование
```

Свойства: (1) нет заранее заданных подозреваемых; (2) любой персонаж, у которого в этом мире
сложились мотив, средства и возможность, может стать виновником; (3) параметр `γ` и пороги
контролируются seed sweep по энтропии распределения виновников.

### Реализация (GEN-006)

Вход стадии — `IncidentSelectionInput`: `ConflictWorld` и `world` (`GeneratedWorld` WorldGen).
CastGen не передаёт мир дальше, поэтому вызывающий код добавляет его к выходу ConflictGen.
Стадия — это `assessIncidents` (оценка) и `selectIncident` (выбор на готовой оценке).

**Мир и владельцы.** Предметы с `ownerArchetype` (с учётом выбранного варианта мира) получают
владельца — первого по id персонажа архетипа. Если архетипа владельца нет в составе, мир нельзя
создать (у предмета нет начального размещения): стадия бросает `GenerationRejection` с кодом
`WORLD_OWNER_ABSENT`, и конвейер перегенерирует мир (§2). Остальные ошибки данных
(`ItemError`, `RangeError`) не перехватываются.

**Присутствие — по симуляции.** Оценка один раз прогоняет распорядки всего состава через
`SimulationRunner` от `historyStartMinutes` до `t = 0` — так же, как HistorySimulation:
персонажи идут шаг за шагом по `LocationGraph.nextTimedStep`, ждут открытия по часам доступа,
проходят только двери, ключи от которых несут, и между локациями находятся в пути (`in_transit`).
«Находится в локации» везде ниже — факт `at` этого прогона, а не плановое место по распорядку.

**Оценка выполнимости** — `assessIncidents(input, content)`; от случайности результат не зависит
(подпоток прогона влияет только на восприятие, которое не используется). Жертвы — персонажи,
чей архетип не входит в `victimConstraints.excludeArchetypes`; шаблоны — из
`preset.incident.templates` с `incidentType` из `types` (чтение полей шаблона —
[scenario-presets.md §4](scenario-presets.md#4-шаблон-преступления-crimesjson)). Для каждой пары
(жертва, шаблон) проверяется **каждый** персонаж, кроме жертвы. Критерии проверяются по порядку,
первый невыполненный учитывается в `rejected`:

1. **motive** — самый сильный `MotiveCandidate(c → v)` не ниже `minMotive`; при равенстве силы —
   меньший `motiveType`.
2. **capable** — личность `c` строго внутри всех границ `requires.traits`.
3. **means** — предмет с тегом (и `itemId`, если задан), который `c` может получить до `t = 0`:
   несёт его с начала предыстории; оказывается в его локации; оказывается в одной локации с его
   владельцем (по распорядку или изменив один блок, см. ниже).
4. **opportunity** — существует совместимая пара «средство — окно»: окно
   `[s, s + minWindowMinutes)` целиком в предыстории в локации со всеми тегами `locationTags`
   (сцена), и всё это время:
   - `c` в сцене, уже держа это средство (взятое не позже минуты `s − 1`);
   - никого другого в сцене нет — спящий тоже свидетель, потому что `SimulationRunner.observe`
     учитывает всех присутствующих; жертва не свидетель, если план направлен на неё;
   - если в плане есть шаг с `target: "$victim"`, жертва в сцене;
   - смерть наступает до начала расследования: при `deathDelayMinutes = [min, max]` есть минута
     `d` в `[s + minWindowMinutes + min, s + minWindowMinutes + max]`, `d < 0`; если в плане нет
     шага на жертву, в минуту `d` жертва находится в сцене.

**Как виновник оказывается в сцене.** Либо распорядок сам держит его в сцене всё окно, а средство
у него уже есть («без изгиба»), либо меняется **один** блок распорядка — одно вхождение блока
`[b0, b1)`. Изменение начинается в минуту `o0 ∈ [b0, b1)` там, где `c` физически находится
минутой раньше (в начале предыстории — в стартовой локации; в пути начинать нельзя), и длится до
конца окна, `s + minWindowMinutes ≤ b1`. В нём `c` идёт за средством (в его локацию или туда, где
в это время его владелец; на месте — одна минута), затем в сцену. Маршрут — пошагово через
`nextTimedStep` с учётом часов доступа всех промежуточных локаций. Ключи от средства действуют
только после того, как оно взято. Если `c` уже в сцене, когда изменение начинается, окно может
начаться раньше `o0`, пока его держит в сцене распорядок. Каждое средство рассматривается
отдельно: время одного и ключи другого не объединяются.

**Средство, которое меняет маршруты.** В `SimulationRunner` каждый персонаж движется независимо:
шаг зависит только от его блока, местоположения и ключей. Поэтому взятое средство меняет
траектории не более двух персонажей, и только если оно само ключ или содержит ключ
(`accessItemIds`), а у `c` с начала его нет: владелец с минуты после получения больше не проходит
свои двери (может оказаться заперт в сцене или не попасть в неё), а распорядок `c` может повести
его другим путём. Для такого средства кандидаты строятся не по базовому прогону, а перебором
**каждой** минуты получения `a` — по распорядку (оба физически в одном месте) или внутри
изменённого блока: траектории владельца и `c` берутся из прогонов этого одного персонажа с
перемещённым средством, остальные — из базового прогона. Минуты, после которых траектории
совпадают, объединяются без потери окон: если персонаж всё время `(a0, a]` физически находится
там, где велит его блок, он не планирует переходов и не читает свои ключи, поэтому получение в
`a0` и в `a` даёт одну траекторию. Из минут с одинаковыми траекториями (и, для изменённого блока,
с тем же вхождением блока и местом) раскрывается только самая ранняя: она допускает все окна
более поздних. Для остальных средств самое раннее получение и самое раннее прибытие доминируют,
и отсев по базовому прогону точен.

**Проверка симуляцией.** Кандидаты каждой сцены по времени начала проверяются повторным прогоном
`SimulationRunner`: изменённый блок задаётся `ScheduleOverride` (до места получения, затем до
сцены), средство переходит к `c` в `ItemRegistry` в минуту после получения. Окно принимается,
если в этом прогоне выполнены все условия выше. Проверка идёт до первого подтверждённого окна,
без ограничения числа кандидатов; оно попадает в `opportunities`, отклонённые считает
`windowsRejectedBySimulation` (при точных кандидатах — 0; ненулевое значение означает расхождение
модели с симуляцией и не приводит к пропуску более позднего окна).

**Оценка кандидата.** `score = 0,5 · motive + 0,3 · opportunityQuality + 0,2 · personalityFit`
(`SCORE_WEIGHTS`), `score ∈ (0, 1]`, округление до 6 знаков.
`opportunityQuality = min(1, число допустимых начал окна по всем сценам / 60)`
(`OPPORTUNITY_SATURATION_MINUTES`; начала считаются по кандидатам до повторной симуляции); `personalityFit` —
средняя глубина внутри границ черт (`(x − gt) / (1 − gt)`, `(lt − x) / lt`), 1 без требований.

**Выбор** (`selectIncident`). Подпотоки `ctx.rng` (`gen/IncidentSelection`):

- `victim` — порядок жертв: взвешенный выбор без возвращения, вес
  `(1 + число партнёров по отношениям) · (1 + число мотивов против неё не ниже порога)`;
- `template/<victimId>` — случайный порядок шаблонов для жертвы;
- `culprit/<victimId>/<templateId>` — для первого шаблона с непустым `feasible`:
  `rng.weighted(feasible, score^γ)`, `γ = preset.incident.gamma ?? 0,7` (`DEFAULT_CULPRIT_GAMMA`).

Результат не зависит от порядка персонажей и мотивов во входе. Если ни для одной пары
(жертва, шаблон) нет допустимого виновника, стадия бросает `GenerationRejection` с кодом
`INCIDENT_NO_FEASIBLE_CULPRIT` и `diagnostics.incidentReport`, и конвейер начинает следующую
попытку (§2).

**Выход** — `IncidentWorld`: вход и

- `incident: IncidentPlan { type, templateId, victimId, culpritId, motive, meansItemIds,
  opportunities, score }`. `opportunities` — по одному подтверждённому самому раннему окну в
  каждой сцене: `{ locationId, from, to, starts, meansItemId, acquisition, deviation, deathAt? }`;
  `acquisition { locationId, at, fromCharacterId? }` — где и когда взято средство (`null`, если
  оно у виновника с начала); `deviation { from, to }` — изменённый блок (`null` без изгиба).
  Это пример выполнимого плана; точные шаги, причину изгиба и алиби строит PlotPlanning (см. ниже);
- `incidentReport: IncidentReport { gamma, victimsEligible, feasibleCulpritCount,
  feasibleTriples, byTemplate, rejected, windowsRejectedBySimulation, chosen }`:
  `feasibleCulpritCount` — число допустимых виновников для выбранных жертвы и шаблона;
  `byTemplate[T]` — жертвы с допустимым виновником, пары (жертва, виновник) и различные виновники
  шаблона `T`; `rejected` — отказы по первому невыполненному критерию. Это истина сервера,
  не для клиентов.

Для seed sweep (например, проверки выполнимости шаблонов сценария) `assessIncidents` выдаёт по
каждому шаблону всех допустимых виновников для всех жертв сгенерированного мира без выбора.

Ограничения MVP:

- окно и смерть — только в предыстории (`t < 0`);
- взятое средство остаётся у виновника: возврат ключа или сокрытие (`conceal`) не моделируются,
  поэтому кража единственного ключа может навсегда закрыть владельцу его локацию;
- получение средства занимает одну минуту на месте; длительности шагов плана и их порядок
  проверяет PlotPlanning;
- окно не может продолжаться после конца изменённого блока, даже если следующий блок распорядка
  снова в сцене;
- полнота поиска гарантируется в пределах этой модели (одно изменённое вхождение блока,
  получение лично, перемещение средства — единственное изменение мира); планы вне её
  (несколько изгибов, возврат ключа) не рассматриваются;
- свидетели и жертва своих распорядков не меняют; влияние присутствия виновника на других
  персонажей (кроме перемещения средства) не моделируется.

### PlotPlanning

`plotPlanning` (`PlotWorld = IncidentWorld + plot`) строит выполнимый план виновника из выбранного
инцидента. Подпотоки `gen/PlotPlanning`: `opportunity` — одно окно из `incident.opportunities`;
`deviation` — причина изгиба; `alibi` — место ложного алиби, если распорядок виновника и так
ведёт на сцену. Выход `plot: PlotPlan`:

- `steps: PlotStepPlan[]` — шаги шаблона в порядке `before`/`after`: `{ id, verb, target, locationId,
  window, duration, optional, acquire }`, совместимые с целями `ExecutePlot` (`id`, `window`,
  `duration`). `acquire` (`take` средства) — в месте и минуту получения из окна (если средство у
  виновника с начала, шага нет), длительностью 1 минута (модель IncidentSelection); остальные шаги
  идут подряд на сцене от `opportunity.from`, окно шага расширено запасом окна. Необязательный шаг,
  не вмещающийся в окно, отбрасывается; обязательные шаги, не вмещающиеся в окно, — ошибка
  контента (`RangeError`);
- `deviation` — не более одного изгиба (`null`, если распорядок сам держит виновника на сцене):
  интервал, причина из `DEVIATION_REASONS` и факт `state` персонажа
  (`property: schedule_deviation`). `overrides` — `ScheduleOverride` ровно как подтверждены
  пересимуляцией (не более двух: в место получения средства, затем на сцену);
- `alibi { claimedLocationId, interval, claim }` — что виновник будет утверждать (`claim` — факт
  `at`, это ложь, не истина);
- `incident` — часть `IncidentRecord` (`type`, `victimIds`, `culpritIds`, `means`, `window`);
  `motive` и `keyEventIds` появятся после предыстории;
- `deathAt` — из окна, если шаблон задаёт отложенную смерть.

`verifyPlot` проверяет порядок и окна шагов, укладывание шагов в окно, маршрут от места получения
до сцены по графу (`nextTimedStep`, со всеми ключами: нижняя оценка времени, точные владения
проверила пересимуляция IncidentSelection), покрытие окна изгибом. Невыполнимый план — отказ
`PLOT_INFEASIBLE`. Исполнение плана — HistorySimulation (GEN-008).

### HistorySimulation

`historySimulation` (`HistoryWorld = PlotWorld + truth, worldState, knowledge,
relationshipsAtStart, locationsAtStart, historyReport`) — предыстория от
`preset.time.historyStartMinutes` до `t = 0`. Истина — то, что сделала симуляция, а не описание
плана. Подпоток `gen/HistorySimulation/simulation` получают `SimulationRunner` и `GoalLoop`.

**Прогон.** `TruthModel` начинается с событий `history` (SocialGen, ConflictGen). Весь состав идёт
по распорядкам через `SimulationRunner` так же, как в проверке IncidentSelection: те же стартовые
локации, `plot.overrides` виновника, средство переходит к виновнику в `ItemRegistry` в минуту
`acquisition.at + 1` (`itemChangeMinutes`). Виновник исполняет `plot.steps` целью `ExecutePlot`
(оценка 1, выше `FollowRoutine`) в `GoalLoop`: шаг начинается в начале своего окна, следующий —
после конца предыдущего. Каждый шаг — событие `covert` с актором-виновником, фактом `did`
(глагол и цель шага) и причиной — предыдущим шагом (первый шаг — событием `harbor_motive` мотива).
Шаг `acquire` (`take` средства) добавляет факт `possessed` до `t = 0` и цель-персонажа, если
средство взято у владельца. Сокрытие (`hide`) средство не перемещает: как и в модели
IncidentSelection, взятое средство остаётся у виновника. Восприятие шагов — `SimulationRunner.observe`
в фазе `WorldEvents` той же минуты.

**Смерть.** Жертва инцидента из `LETHAL_INCIDENT_TYPES` (`murder`) умирает в `plot.deathAt`
(отложенная смерть), иначе в конце смертельного шага: первого шага на жертву, без него — первого
шага на месте. С этой минуты жертва — `exits` раннера: её шаги заканчиваются там, переход, который
пришёл бы позже, не начинается, а наблюдений нет. Событие `die` (`public`, актор — жертва, причина —
смертельный шаг) содержит `state(alive = false)` и `at` тела в месте смерти на `[d, 0)`
(truth-model.md §4, «Смерть»). Смерть в минуту `0` или позже — проблема плана.

**Проверка и перенос.** После прогона каждый шаг сверяется с истиной: шаг исполнен; виновник в
локации шага всё время шага; на шаге на месте нет никого, кроме виновника и (если план направлен на
неё) жертвы; на шаге на жертву она в локации; при получении средство (с учётом контейнеров) лежит
в локации или у владельца, который там же; отложенная смерть без шага на жертву — на месте
преступления. Если проверка не прошла (например, вошёл свидетель), шаги на месте сдвигаются на
`shift = 1, 2, …` минут внутри своих окон (не больше наименьшего запаса окна `maxShift`; шаг
получения не сдвигается) и предыстория симулируется заново с начала. Первый сдвиг без проблем
принимается. Если подходящего сдвига нет, стадия бросает `GenerationRejection` с кодом
`HISTORY_PLOT_FRUSTRATED` и `diagnostics.attempts` (проблемы каждого сдвига), и конвейер начинает
следующую попытку (§2). Подменять исполнение готовыми событиями стадия не может.

**Знания и отношения.** После принятого прогона встречи (SIM-003) находятся по интервалам
присутствия живых (тело собеседником не считается) и обрабатываются по порядку: события `talk`,
пересказ и дрейф отношений на копии графа (`relationshipsAtStart`; вход не меняется). До LiePolicy
(GEN-010) виновник не пересказывает свои действия (`did`), мотив и присутствие на месте
преступления. `knowledge` — хранилища раннера после встреч.

**Выход.** `IncidentRecord` = `plot.incident` + `motive` (`factId(motiveFact(incident.motive))`,
факт события `harbor_motive`) + `keyEventIds` — события исполненных шагов: сначала шаги на месте в
порядке плана (локация первого — место инцидента для валидатора), затем получение средства.
`worldState` — локации и реестр предметов после предыстории, `locationsAtStart` — где каждый
(или тело) находится в `t = 0`. `historyReport { attempts, maxShift, steps, deathAt,
simulatedEvents, encounters }` — серверная диагностика, не для клиентов.

**Проверки (GEN-008).** `npx vitest run packages/generator/test/properties/history-sim.prop.test.ts`:
1000 seed `_test_minimal` — 1000 планов, все исполнены с первой попытки, без сдвигов; 1000 seed
`sanatorium_winter` — 301 план (остальные отклоняются раньше), все исполнены без сдвигов;
`checkTruthInvariants` пуст во всех. Время стадии —
`node --experimental-transform-types packages/generator/test/performance/history-sim.ts` (лучшее из
5 после прогрева по 20 мирам, 2026-11-25): `_test_minimal` (60 минут) — медиана 3,6 мс, максимум
4,8 мс; `sanatorium_winter` (1440 минут) — медиана 48,9 мс, максимум 72,3 мс; бюджет — 200 мс
(ADR 0013).

Ограничения MVP:

- траектории в предыстории совпадают с прогоном IncidentSelection (персонажи движутся независимо,
  прятанье средства его не перемещает), поэтому срыв плана возможен только при расхождении модели
  и симуляции; перенос и отказ покрыты тестами на изменённых распорядках;
- цели SIM-005 (`ConcealEvidence`, `MeetCharacter` и другие) в предыстории не подключены;
- начальные убеждения о предыстории (отношения, секреты `knownBy`) в хранилища не записываются.

### EvidenceGen

`evidenceGen: Stage<HistoryWorld, EvidenceWorld>` не добавляет своей случайности, кроме
распределения `captureMode`. Шаги:

1. `deriveTraces` (EVD-001) применяет `trace-rules.json` к журналу предыстории → `traces`
   (в том числе `testimonial`: их использует TestimonyGen).
2. Для следов `physical`/`document`/`digital` строится `ClueRule` по шаблону следа: документ
   читается (`read`, `documentId = template`), остальное осматривается (`examineHotspot`,
   `hotspotId = template`) в точке следа. `testimonial` улик не даёт (GEN-010).
   `deriveClues` (EVD-002) создаёт `clues`.
3. `requiredClueIds` — улики событий `IncidentRecord.keyEventIds`. Если у какого-то ключевого события
   улики нет, стадия бросает `GenerationRejection('EVIDENCE_KEY_EVENT_UNCOVERED')`.
4. `distributeCaptureModes` (EVD-003) доводит долю `qr` среди обязательных улик до
   `preset.phone.minQrShare`.

Выход `EvidenceWorld` = `HistoryWorld` + `traces`, `clues`, `requiredClueIds`.

### TestimonyGen

`testimonyGen: Stage<EvidenceWorld, TestimonyWorld>` (GEN-010, GEN-014). Случайность — только выбор
свидетеля мотива (подпоток `motive-witness`).

1. Копирует хранилища знаний (вход не меняется) и записывает в них секреты: каждый `SocialSecret`
   попадает в хранилище тех, кто в `knownBy` (субъект — `observed`, собеседник — `told`). До этой
   стадии секреты в хранилищах не лежали, а скрывать можно только то, что знаешь (KNOW-002).
2. Строит `LieMotive` каждого персонажа: его собственные секреты (защищается факт секрета,
   запасной ответ — отрицание: то же `state` со значением `false`) и, для виновника, «вину» —
   его `did` ключевых событий (запасной ответ — «просто был там»: `did stay` в ту же минуту и в том
   же месте), мотив и обладание средством.
   Ложь виновника выдаётся лишь та, которую достижимая улика может опровергнуть (GEN-014): `did`
   «просто был там» в том же месте и любая подмена `state` неопровержимы, поэтому у виновника
   `alternatives` пуст для них, и он молчит, а не лжёт (`V-LIES-BREAKABLE` не ослаблен; вопрос
   об обратном — [OQ-24](../planning/open-questions.md)).
3. Мотив (OQ-20): `motive`-факт виновника записывается как `told` (от виновника) в хранилище одного
   живого свидетеля, не виновника и не жертвы (выбор из отсортированного состава по подпотоку).
   На вопрос о виновнике он повторяет это показание; для солвера это `testimony(w, motive(c,v))`,
   правило `motive_from_testimony` выводит `motive`.
4. `buildLiePolicy` даёт `LiePolicy`: скрывается только известное, подделка — только при
   `honesty < 0.75`. Персонаж без мотива получает пустую политику.

Выход `TestimonyWorld` = `EvidenceWorld` + `knowledge` (с секретами), `lieMotives`,
`liePolicies` (на каждого персонажа), `testimonyReport { concealing, lying, honest, secretBeliefs }`.
Свидетельские следы (`testimonial`) этой стадией не потребляются: показания по ним строит
`answer`; отдельные записи в `Investigation` — задача Packaging.

### RedHerrings

`redHerrings: Stage<TestimonyWorld, RedHerringWorld>` (GEN-010). Для 1–3 секретов невиновных
(`about` не виновник и не жертва; не более одного проступка на персонажа) добавляет в истину
**настоящее** событие проступка и выводит его следы и улики:

- глагол — из правил следов без условия `when`, чьи следы лежат в месте события, без `requires` и
  утверждают только `presence(...)` (в sanatorium и `_test_minimal` — `hide`, `destroy`): проступок
  не даёт ни `means`, ни `opportunity`, поэтому не связывает невиновного с инцидентом;
- время и место — свободная минута `at`-пребывания персонажа внутри предыстории, не ближе
  `INCIDENT_MARGIN_MINUTES` (60) к окну инцидента и не в месте ключевых событий; событие — на
  том же месте, где персонаж был по истине (инварианты `checkTruthInvariants` сохраняются);
- события не входят в `keyEventIds`, их улики не входят в `requiredClueIds`;
- проступок становится воспоминанием персонажа (`did`), который он скрывает; при `honesty < 0.75` он
  говорит «просто был там» (`did stay`), иначе молчит. Политика персонажа пересобирается.

Вход не изменяется: `truth` — копия с добавленными событиями. Если ни у одного невиновного нет
подходящего пребывания (короткие сценарии: `_test_minimal` идёт 60 минут), проступков 0 и стадия
не отклоняет попытку.

Выход `RedHerringWorld` = `TestimonyWorld` + `truth`, `traces`, `clues` (с добавленными),
`redHerrings: { secretId, characterId, eventId, traceIds, clueIds }[]` и
`redHerringReport { count, clues, traces }` — число ложных следов (`clues`) для серверных отчётов.

Проверки: `npx vitest run packages/generator/test/properties/testimony-red-herrings.prop.test.ts` —
60 входов `sanatorium_winter` (общий кэш `test/support/evidence.ts`, около 6 с): каждый ложный след
ссылается на реальное событие истины невиновного, инварианты истины чисты, обязательные улики
не тронуты, проступков 1–3, ложь только из политики; 30 входов `_test_minimal`.

### Validation и Packaging (GEN-011)

`generateInvestigation({ scenarioId, seed }, content, options?)` собирает цепочку стадий 1–10
(`worldGen` → `CastGen` → … → `redHerrings`; мир `GeneratedWorld` проносится рядом со значением до
`IncidentSelection`) и запускает её через `runPipeline` с предикатом `accepts` — шлюзом валидации
(ADR 0006). Для каждой попытки, дошедшей до шлюза:

1. **Packaging** (`packageInvestigation`): `InvestigationBuilder` с миром после предыстории
   (`worldState`), персонажами, `relationshipsAtStart`, истиной (с проступками RedHerrings) и секретами
   `{ id, fact, knownBy }`.
2. Контекст проверок: `clues`, `requiredClueIds`, `minQrShare`, `deductionRules` (скомпилированные),
   `startLocationId`, показания `testimony` — ответы каждого персонажа на вопросы «где вы были в окне
   инцидента», «о себе», «что знаете о X» (для каждого X) в минуту 0; `statements` — те же без `veracity`.
   `historyStartMinutes` — минимум из начала предыстории пресета и самого раннего события: события
   `SocialGen` и `ConflictGen` (отношения, секреты, мотивы) лежат за годы до симулируемой предыстории.
3. Проверки `GENERATION_CHECKS` = `V-TRUTH-INV`, `V-TIMELINE`, `V-PHONE-REQUIRED`, солвер
   (`V-REACHABLE`, `V-CULPRIT-PROVABLE`, `V-UNIQUE`), `V-LIES-BREAKABLE`, `V-TESTIMONY`. Если ошибок
   нет, добавляется `V-DETERMINISM`: попытка повторяется (`runPipeline` с `firstAttempt`) и
   `investigationHash` двух прогонов сравнивается. Список проверок можно заменить опцией `checks`.
4. Ошибка проверки отклоняет попытку; следующая попытка — это **ремонт перегенерацией** с подсидом
   `<seed>#N` с первой стадии (стратегии 3–4 из [validation.md §4](../investigation/validation.md)
   сведены в одну; стратегии 1–2, меняющие готовое дело, не реализованы). Максимум 8 попыток.

Результат: `{ ok: true, investigation, investigationHash, report, server }` или
`{ ok: false, error: 'GENERATION_UNSOLVABLE', report }`. `report.validations[]` хранит для каждой
попытки найденные проверками ошибки и предупреждения (`checkId`, `code`, `message`).

**Серверный результат (GEN-013).** `server: ServerGenerationPayload` — закрытые данные принятой
попытки для настройки портов движка без повторной генерации: `attempt` (номер принятой попытки),
`startLocationId`, `clues`, `requiredClueIds`, `knowledge` и `liePolicies` (по каждому персонажу
каста), `testimony` (с `veracity`), `statements` (те же без `veracity`) и скомпилированные
`deductionRules`. Шлюз запоминает попытку, которую он пропустил (вместе с её `Investigation` и
контекстом проверок), и результат собирается из **тех же объектов**, что проверялись; данные
отклонённых попыток и повтора `V-DETERMINISM` в него не попадают, `investigationHash` не меняется.
При неудаче поля `server` нет. Payload называет истину (обязательные улики, правдивость показаний,
политики лжи), поэтому не попадает в `PlayerView`/`PhoneView`, тела REST, логи и вывод `hs-gen`
(даже с `--debug-truth`) и не пишется в сохранения. Подключение к портам `GameEngine` на сервере —
отдельная задача; `AccusationPort.hallucinatedClueIds` и `incident` генератор не формирует.

**Состояние на GEN-014** (решения OQ-19, OQ-20). Шлюз по умолчанию пропускает `_test_minimal`
(проверено на 200 seed, 0 отказов с первой попытки; тест `gate.test.ts` — 25 seed без урезания
`checks`). Что для этого сделано: `motive` доказывает показание свидетеля (`motive_from_testimony`);
`means` и `opportunity` берутся из следа взятия записи (`took_record`) и из следа «был здесь»;
невиновных исключает `no_access_from_record` или `alibi_from_witness` по следу
`visitor_register` с `presence(c, loc, $span)` на весь интервал стоянки; ложь виновника, которую
нечем опровергнуть, не выдаётся. `sanatorium_winter`: `means` и `motive` доказываются, `opportunity`
по записям `duty_log_entry`, но часть seed всё ещё отклоняется: невиновный, который перемещался в
окне инцидента, не покрыт ни одной записью о стоянке на весь интервал (`NOT_UNIQUE`), а у части seed
все 8 попыток дают `INCIDENT_NO_FEASIBLE_CULPRIT` (выбор инцидента, не шлюз). Доля прохождения
на seed 1–40: 24 из 40. Полный набор следов — CNT-004.

### CLI `hs-gen`

```bash
node --experimental-transform-types packages/generator/bin/hs-gen.ts --scenario _test_minimal --seed 42 [--debug-truth]
```

Без `--debug-truth` печатает только публичное: `ok`, `scenarioId`, `seed`, `generatorVersion`,
`attempts`, `investigationHash`; при неудаче — `error` и коды причин каждой попытки (без текстов,
они называют персонажей). С `--debug-truth` добавляет снимок всего `Investigation` (с истиной) и
`GenerationReport`. Код выхода: 0 — успех, 1 — `GENERATION_UNSOLVABLE`, 2 — ошибка аргументов.

## 4. Отчёт генерации

`InvestigationReport { seed, generatorVersion, attempts: AttemptReport[], validations: AttemptValidation[],
feasibleCulpritCount?, chosen?: { victimArchetype, culpritArchetype, template, motiveType } }` —
**не** отдаётся клиентам (содержит истину), сохраняется в отчётах sweep и debug-логах.
`runPipeline` заполняет `seed`, `generatorVersion` и `attempts` (с `rejection` отклонённых попыток,
длительностью стадий в `timingsMs`); `generateInvestigation` добавляет `validations` и, для принятого
дела, `feasibleCulpritCount` и `chosen` из `IncidentReport`.

## 5. Расширяемость

- Новый сценарий = новый пресет (данные). Если пресету нужна новая механика (новый глагол, тип
  следа, тип мотива) — она добавляется в словари ядра отдельной задачей, а не в пресет.
- Новая стадия добавляется в список стадий с собственным подпотоком; существующие результаты
  не меняются, но `GENERATOR_VERSION` увеличивается.
