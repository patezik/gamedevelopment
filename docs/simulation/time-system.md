# Time & Schedule System

Модуль `@hs/core/time`. Интерфейсы — [modules.md §2](../architecture/modules.md).

## 1. Модель времени

- Единица — **игровая минута**, тип `GameMinutes` (целое). `t = 0` — начало игры по пресету.
  Предыстория генерации использует `t < 0`.
- Отображение (день, чч:мм, период суток) вычисляет `Calendar` из `preset.time.startDateTime`.
  Это единственное место, где существует календарная дата.
- Периоды суток (`DayPeriod`): `morning` 06:00–11:59, `day` 12:00–17:59, `evening` 18:00–21:59,
  `night` 22:00–05:59. Периоды влияют на освещение локаций, расписания и угрозы.
- Сценарий: `durationMinutes` (MVP: 4320 = 3 дня); `t ≥ durationMinutes` — конец сценария.

## 2. Единственный механизм продвижения

**Только `TimeSystem.advance(minutes)` двигает часы.** Никаких независимых таймеров в механиках.
Все действия игрока передают стоимость в `GameEngine.dispatch`, который вызывает `advance`.

```
advance(m):
  target = min(now + m, scenarioEnd)
  пока есть событие e с e.at ≤ target (в порядке ключа сортировки):
     now = e.at
     handler(e.kind).handle(e)        // может планировать новые события (≥ now)
     если handler запросил прерывание и действие прерываемое → остановиться, вернуть interruptedAt
  now = target
  эмитировать ClockAdvanced(from, to) и PeriodChanged/DayChanged при пересечении границ
```

### Порядок одновременных событий

Ключ сортировки: `(at, phase, priority, seq)`:

| Фаза | `TickPhase` | Что обрабатывается |
|------|-------------|--------------------|
| 0 | `Calendar` | смена периода/дня, освещение |
| 1 | `Schedules` | начало/конец блоков расписаний NPC |
| 2 | `Simulation` | шаги активностей NPC, встречи, наблюдения |
| 3 | `WorldEvents` | сюжетные/критические события пресета, вторичные инциденты |
| 4 | `Availability` | открытие/закрытие локаций, доступность персонажей |
| 5 | `Timers` | истечение окон улик, разряд телефона, рост Static, угрозы |
| 6 | `Outcome` | дедлайны, условия победы/поражения |

`priority` — внутри фазы (меньше — раньше); `seq` — порядок планирования (стабилен при
детерминированном исполнении). Так одновременные события всегда разрешаются одинаково.

## 3. Стоимость действий

`ActionCostTable` — данные пресета (с дефолтами ядра):

```json
{ "move": { "base": "graph" }, "examineLocation": { "base": 15 }, "examineHotspot": { "base": 5 },
  "captureEvidence": { "base": 2 }, "talk": { "base": 10 }, "interrogate": { "base": 20 },
  "call": { "base": 5, "plus": "conversation" }, "message": { "base": 2 }, "read": { "base": 10 },
  "pickLock": { "base": 20, "onFail": 10 }, "useItem": { "base": 5 }, "rest": { "choices": [60, 120, 240] },
  "wait": { "range": [15, 120], "step": 15 } }
```

`resolveActionCost(action, ctx)` применяет модификаторы (усталость, травма, темнота, рассудок)
и **округляет до целых минут**. Клиент получает оценку стоимости в `PlayerView.availableActions[].costPreview`
до подтверждения; фактическая стоимость может отличаться только при исходе проверки
(вскрытие замка), что указано в интерфейсе («20–30 мин»).

## 4. Прерывания

Долгие действия (`rest`, `wait`, `pickLock`, звонок) прерываемы. Обработчик может запросить
прерывание, если событие требует внимания игрока: NPC вошёл в локацию игрока, входящий звонок,
угроза, критическое событие. Потраченное время = фактически прошедшее; эффект действия
пропорционален (отдых 37 из 60 минут → восстановление по 37 минутам).

## 5. Влияние времени на мир

После каждого `advance` обновляются, в порядке фаз: календарь → расписания NPC → симуляция →
очередь сюжетных событий → доступность локаций → таймеры улик/угроз → условия исхода →
(вне ядра) интерфейс часов в Godot и статус-бар телефона через `view.update`.

**Пропуск событий.** Событие с `requiresPresence` (например, встреча двух NPC в оранжерее в
21:00), при котором игрок не присутствовал, порождает `ScheduledEventMissed` во внутреннем
журнале: информация из него доступна только косвенно (следы, пересказ свидетелей).

## 6. Сценарии разной длительности

`durationMinutes`, `criticalEvents`, `deadlines`, `endConditions` — из пресета. Досрочное
завершение — обвинение, гибель, безумие или условие пресета. Пропуск критического события
задаётся в пресете (`onMissed`: эффект на Static, вторичный инцидент, закрытие локации).

## 7. Сохранение

`TimeSystem` сериализует `now`, состояние `Scheduler` (включая `seq`-счётчик) и состояние RNG
подпотоков. Восстановление из снимка + повтор действий даёт идентичный `stateHash`
([ADR 0014](../architecture/adr/0014-save-system.md)).

## 8. Обязательные тесты (TIME-*)

1. Продвижение после каждого типа действия на стоимость из таблицы (табличный тест).
2. Переходы 59→60 минут, 23:59→00:00 (смена дня), границы периодов.
3. Событие ровно в `target` обрабатывается; событие в `target + 1` — нет.
4. Порядок одновременных событий разных фаз и одинаковой фазы (по `priority`, затем `seq`).
5. Расписания NPC: персонаж в нужной локации в начале блока (интеграция с SIM).
6. Пропуск события: `ScheduledEventMissed` при отсутствии игрока.
7. Сценарии 1 день / 3 дня / 7 дней (property-тест по `durationMinutes`).
8. Сохранение/загрузка посреди очереди событий → одинаковый хеш.
9. Прерывание долгого действия и пропорциональный эффект.
10. Взаимодействие с Character Simulation: 24 часа предыстории дают одинаковый журнал при одинаковом seed.
