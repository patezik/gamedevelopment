# Time & Schedule System

Модуль `@hs/core/time`. Интерфейсы — [modules.md §2](../architecture/modules.md).

## 1. Модель времени

- Единица — **игровая минута**, тип `GameMinutes` (целое). `t = 0` — начало игры по пресету.
  Предыстория генерации использует `t < 0`.
- Отображение (день, чч:мм, период суток) вычисляет `Calendar` из `preset.time.startDateTime`.
  Это единственное место, где существует календарная дата.
  - `startDateTime` — «настенное» локальное время `YYYY-MM-DDTHH:mm[:00]` без часового пояса
    (суффиксы `Z` и `±hh:mm`, ненулевые секунды, доли секунды и несуществующие даты отклоняются).
    Загрузчик пресетов и `Calendar` используют общий разбор. Даты считаются арифметически,
    без `Date`, поэтому результат не зависит от окружения.
  - День 1 начинается в полночь даты старта, поэтому `t < 0` остаётся в дне 1 до полуночи; дальше
    идут день 0, −1 и т. д. (предыстория).
  - `toDisplay(t)` возвращает `dateIso` в формате `YYYY-MM-DDTHH:mm:00`; `format(t)` — `День 2, 21:40`.
    Нецелое `t` — `RangeError`.
- Периоды суток (`DayPeriod`): `morning` 06:00–11:59, `day` 12:00–17:59, `evening` 18:00–21:59,
  `night` 22:00–05:59. Периоды влияют на освещение локаций, расписания и угрозы.
- Сценарий: `durationMinutes` (MVP: 4320 = 3 дня); `t ≥ durationMinutes` — конец сценария.

## 2. Единственный механизм продвижения

**Только `TimeSystem.advance(minutes)` двигает часы.** Никаких независимых таймеров в механиках.
Все действия игрока передают стоимость в `GameEngine.dispatch`, который вызывает `advance`.

```
advance(m):
  target = min(now + m, scenarioEnd)
  пока есть событие e с e.at ≤ target (в порядке ключа сортировки):
     now = e.at
     handler(e.kind).handle(e)        // может планировать новые события (≥ now)
     если handler запросил прерывание и действие прерываемое → записать interruptedAt и выйти из цикла
  если прерывания не было: now = target
  вернуть ClockAdvanced(from, to) и PeriodChanged/DayChanged при пересечении границ
```

`TimeSystem` создаётся с календарём, минутой окончания сценария и необязательной начальной
минутой для предыстории. `registerHandler` закрепляет фазу за видом события. `schedule` берёт фазу
у зарегистрированного обработчика. Обработчик может планировать и отменять события через
`TickContext`. Новые события сортируются вместе с остальными ожидающими событиями.

`AdvanceResult.events` начинается с `ClockAdvanced`, за которым идут события пересечённых
границ в порядке времени. События границ формируются для интервала `from < at ≤ to`.
При прерывании `to` равен `interruptedAt`, а последующие события остаются в очереди.
При запросе за конец сценария и достижении конца результат содержит
`limit: 'TIME_BEYOND_SCENARIO_END'`. Запланированные на последнюю минуту события Outcome
обрабатываются в очереди в своей фазе. Правила и условия исходов задаются в TIME-005.

### Порядок одновременных событий

Ключ сортировки: `(at, phase, priority, seq)`:

| Фаза | `TickPhase` | Что обрабатывается |
|------|-------------|--------------------|
| 0 | `Calendar` | смена периода/дня, освещение |
| 1 | `Schedules` | начало/конец блоков расписаний NPC |
| 2 | `Simulation` | шаги активностей NPC, встречи, наблюдения |
| 3 | `WorldEvents` | сюжетные/критические события пресета, вторичные инциденты |
| 4 | `Availability` | открытие/закрытие локаций, доступность персонажей |
| 5 | `Timers` | истечение окон улик, разряд телефона, рост Static, угрозы |
| 6 | `Outcome` | дедлайны, условия победы/поражения |

`priority` — внутри фазы (меньше — раньше); `seq` — порядок планирования (стабилен при
детерминированном исполнении). Так одновременные события всегда разрешаются одинаково.

### Scheduler

`Scheduler` (`packages/core/src/time/scheduler.ts`) — двоичная куча по полному ключу
`(at, phase, priority, seq)`. `seq` уникален, поэтому порядок строго определён и не зависит от формы
кучи. Куча выбрана вместо отсортированного массива: вставка и извлечение O(log n) против O(n) сдвигов
на вставку. Замер 100 000 вставок и извлечений с порогом 200 мс запускается отдельно от сбора покрытия
командой `node packages/core/test/performance/scheduler.ts`. Отмена ленивая; при большом числе отменённых
записей куча перестраивается.

- Идентификатор события — `evt_<seq>`. Счётчик `seq` входит в снимок, поэтому после восстановления
  новые события получают те же идентификаторы и тот же порядок, что без перезагрузки.
- У планировщика своё время `now`: `at` последнего извлечённого события или `t` последнего
  `popDue`. Планирование раньше `now` — `SCHEDULER_PAST_EVENT`, ровно в `now` — допустимо. Время
  никогда не идёт назад. Для предыстории (`t < 0`) создавайте `new Scheduler(historyStartMinutes)`.
- **Цикл `advance` должен использовать `popNext(target)`**, а не `popDue(target)`: обработчик может
  запланировать событие между уже ожидающими (`A@10` планирует `C@15`, пока ждёт `B@20`: порядок
  `A, C, B`). `popDue` отдаёт весь пакет до запуска обработчиков, поэтому порядок в нём не восстановить.
  По завершении цикла `popDue(target)` вернёт `[]` и переведёт `now` на `target`.
- `serialize()` возвращает независимую JSON-копию (`now`, `nextSeq`, события в порядке обработки).
  `payload` должен быть каноническим JSON: `undefined`, `NaN`, `Infinity` приводят к ошибке при
  сериализации. `Scheduler.restore(state)` проверяет снимок и бросает `SCHEDULER_INVALID_STATE`
  при повреждении (дубликаты, `id` не соответствует `seq`, событие раньше `now`, лишние поля).
- События хранятся замороженными; `payload` — по ссылке и считается неизменяемым.

## 3. Стоимость действий

`ActionCostTable` — данные пресета (с дефолтами ядра):

```json
{ "move": { "base": "graph" }, "examineLocation": { "base": 15 }, "examineHotspot": { "base": 5 },
  "captureEvidence": { "base": 2 }, "talk": { "base": 10 }, "interrogate": { "base": 20 },
  "call": { "base": 5, "plus": "conversation" }, "message": { "base": 2 }, "read": { "base": 10 },
  "pickLock": { "base": 20, "onFail": 10 }, "useItem": { "base": 5 }, "rest": { "choices": [60, 120, 240] },
  "wait": { "range": [15, 120], "step": 15 } }
```

`resolveActionCost(action, ctx)` применяет модификаторы (усталость, травма, темнота, рассудок)
и **округляет до целых минут**. Клиент получает оценку стоимости в `PlayerView.availableActions[].costPreview`
до подтверждения; фактическая стоимость может отличаться только при исходе проверки
(вскрытие замка), что указано в интерфейсе («20–30 мин»).

Реализация — `packages/core/src/time/action-cost.ts`:

- **Таблица.** `DEFAULT_ACTION_COSTS` — таблица выше; `createActionCostTable(overrides)` накладывает
  переопределения пресета по отдельным действиям (остальные остаются по умолчанию). Неизвестное
  действие или неверная форма правила — `COST_TABLE_INVALID`. Допустимые формы: `{ base: N }`,
  `{ base: "graph" }`, `{ base: N, plus: "conversation" }`, `{ base: N, onFail: M }`,
  `{ choices: [...] }` (строго по возрастанию), `{ range: [от, до], step }` (`до` достижимо шагами).
  Действия со стоимостью: `move`, `examineLocation`, `examineHotspot`, `captureEvidence`, `talk`,
  `interrogate`, `call`, `message`, `read`, `pickLock`, `useItem`, `rest`, `wait`.
- **Результат** `{ min, max, expected }` в целых минутах: `min`/`max` — границы того, что можно
  списать, `expected` — стоимость без неожиданностей. Для `pickLock` это `{ 20, 30, 20 }`; для
  `rest`/`wait` без выбранной длительности — весь диапазон с `expected = min`, а с `ctx.minutes` —
  точная стоимость (длительность вне `choices`/`range`+`step` — `ACTION_INVALID`).
- **`move`** берёт время маршрута из `ctx.travel.provider` (`TravelTimeProvider`, ему
  структурно соответствует `LocationGraph`); `time` стоит ниже `world`, поэтому сам граф не
  импортирует. Маршрута нет (`null`) — `ACTION_INVALID`; исключения провайдера (например,
  неизвестная локация) не перехватываются. Для маршрута с учётом персонажа оберните граф:
  `{ travelTime: (from, to) => graph.travelTime(from, to, actor) }`. `call` добавляет
  `ctx.conversationMinutes` (по умолчанию 0).
- **Модификаторы** (`CostModifier`: `id`, `order`, `apply(minutes, action, ctx)`) применяются в порядке
  `(order, id)`, а не в порядке массива. Они получают и возвращают дробные минуты; округление
  делается **один раз** в конце (с поправкой на погрешность float: `50 × 1.15` даёт 58, а не 57),
  результат не меньше 0. Умножение и сложение не коммутируют, поэтому `order` — часть контракта:
  `(10 × 1,25) + 5` ≠ `(10 + 5) × 1,25`. Модификаторы должны быть монотонными; иначе диапазон
  всё равно приводится к `min ≤ expected ≤ max`.
- **Ошибки:** `ACTION_INVALID` (неизвестное действие, нет `ctx.travel`, недопустимая
  длительность, нет маршрута), `COST_TABLE_INVALID` (неверная таблица пресета).

## 4. Прерывания

Долгие действия (`rest`, `wait`, `pickLock`, звонок) прерываемы. Обработчик может запросить
прерывание, если событие требует внимания игрока: NPC вошёл в локацию игрока, входящий звонок,
угроза, критическое событие. Потраченное время = фактически прошедшее; эффект действия
пропорционален (отдых 37 из 60 минут → восстановление по 37 минутам).

## 5. Влияние времени на мир

После каждого `advance` обновляются, в порядке фаз: календарь → расписания NPC → симуляция →
очередь сюжетных событий → доступность локаций → таймеры улик/угроз → условия исхода →
(вне ядра) интерфейс часов в Godot и статус-бар телефона через `view.update`.

**Пропуск событий.** Событие с `requiresPresence` (например, встреча двух NPC в оранжерее в
21:00), при котором игрок не присутствовал, порождает `ScheduledEventMissed` во внутреннем
журнале: информация из него доступна только косвенно (следы, пересказ свидетелей).

## 6. Сценарии разной длительности

`durationMinutes`, `criticalEvents`, `deadlines`, `endConditions` — из пресета. Досрочное
завершение — обвинение, гибель, безумие или условие пресета. Пропуск критического события
задаётся в пресете (`onMissed`: эффект на Static, вторичный инцидент, закрытие локации).

## 7. Сохранение

`TimeSystem` сериализует `now`, состояние `Scheduler` (включая `seq`-счётчик) и состояние RNG
подпотоков. Восстановление из снимка + повтор действий даёт идентичный `stateHash`
([ADR 0014](../architecture/adr/0014-save-system.md)).

## 8. Обязательные тесты (TIME-*)

1. Продвижение после каждого типа действия на стоимость из таблицы (табличный тест).
2. Переходы 59→60 минут, 23:59→00:00 (смена дня), границы периодов.
3. Событие ровно в `target` обрабатывается; событие в `target + 1` — нет.
4. Порядок одновременных событий разных фаз и одинаковой фазы (по `priority`, затем `seq`).
5. Расписания NPC: персонаж в нужной локации в начале блока (интеграция с SIM).
6. Пропуск события: `ScheduledEventMissed` при отсутствии игрока.
7. Сценарии 1 день / 3 дня / 7 дней (property-тест по `durationMinutes`).
8. Сохранение/загрузка посреди очереди событий → одинаковый хеш.
9. Прерывание долгого действия и пропорциональный эффект.
10. Взаимодействие с Character Simulation: 24 часа предыстории дают одинаковый журнал при одинаковом seed.
